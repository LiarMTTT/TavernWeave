# 无障碍与包容设计

行业层：人怎么感知、操作、理解界面；规范、模式、认知与游戏三条轴怎么叠。本页是机制蒸馏，不是某仓库的皮肤或合规声明。对比度与动效底线见 [[concepts/视觉CSS与设计token]]，本页不重复那一节。

## 一句话定义

无障碍是可测的内容合同（现行枢纽是 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)）；包容设计是从排除出发的方法；通用设计是「尽量一份设计服务所有人」。三者相关，不是同义词。

## 为什么重要

HUD、表单、空面板和命令面板都会把人挡在门外：焦点出不去、字段错只闪一下、空白区看不出是空还是还在加载、快捷命令没有键盘模型。规范回答「能不能声称符合」；模式回答「这个控件怎么键鼠」；认知与游戏指南回答「规范没盖住的使用需求」。混用会把 Note 当成 Rec，或把游戏清单当成法律清单。

## 如何运作

### 规范层：WCAG 是 Rec，APG 不是

[WCAG 2.2](https://www.w3.org/TR/WCAG22/) 是 W3C Recommendation（现行公布页日期 2024-12-12；首发 2023-10-05）。四条原则：可感知、可操作、可理解、健壮。符合性看可测成功标准（A / AA / AAA），不是看「有没有跟一篇模式文」。2.0 / 2.1 / 2.2 都仍是现行 Rec；后一版加条、不改旧条（2.2 把 4.1.1 Parsing 标过时）。[WCAG 总览](https://www.w3.org/WAI/standards-guidelines/wcag/) 写明：WCAG 是给要技术标准的人用的，不是入门课。WCAG 3 仍是早期草案。

[ARIA Authoring Practices Guide (APG)](https://www.w3.org/WAI/ARIA/apg/) 教怎么把 ARIA 语义和键盘行为落到常见控件。它是模式指南，合成若干规范的用法，**不是** W3C Recommendation。跟了 APG 示例 ≠ 自动符合 WCAG。APG 自己写：角色是承诺，错误 ARIA 比不用更糟；示例按 ARIA 1.2 说明正确用法，不负责给浏览器/读屏缺口打补丁。采集日读屏基线记 [NVDA](https://www.nvaccess.org/) 2026.1.1；WAI Easy Checks 迁址后新页当时是空壳，不当活清单。

### 方法层：包容 ≠ 无障碍 ≠ 通用

[Microsoft Inclusive Design](https://inclusive.microsoft.design/) 把包容设计写成方法：承认排除、向多样性学、为一人解再扩到多人。工具包（如 Inclusive 101）许可是 **CC BY-NC-ND**，可引用不可当商用改作素材。无障碍通常指对照 WCAG 等标准去掉障碍。通用设计（Ron Mace 传统）追求一份设计尽量不用适配就服务所有人。包容设计承认情境错配，不承诺「一个控件打天下」。

### 认知层：COGA Note 不构成符合性

[WAI Cognitive](https://www.w3.org/WAI/cognitive/) 写明：WCAG 已覆盖一部分认知需求（够时间、可读、可预期、输入帮助等），仍有需求不在现行标准里。[Making Content Usable（COGA）](https://www.w3.org/TR/coga-usable/) 是 2021-04-29 Working Group Note，摘要写：遵循它**不是** WCAG 符合性要求。补充目标/模式同样「超出 WCAG 2 才要求的部分」。

三套语言合同不可互换：[Digital.gov Plain Language](https://digital.gov/guides/plain-language) 是美国联邦「写给特定读者、清楚简洁」；`plainlanguage.gov` 已重定向到 Digital.gov。[Easy Read / Easy-to-Read](https://www.inclusion-europe.eu/easy-to-read/) 是短句 + 配图、面向智力障碍等读者的版式。COGA 是认知无障碍目标与模式。把其中一套当成另外两套的符合性证明，会漏人。

### 游戏层：GAG / XAG / APX 三轴

[Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/) 自 2012 起按基本 / 中等 / 复杂分档，是行业参考清单。[Xbox Accessibility Guidelines](https://learn.microsoft.com/en-us/gaming/accessibility/guidelines) 现行 **v3.2**（2023-06-08）；文档写明给设计/开发/测试当护栏，**不是**任何法律或合规清单。[Accessible Player Experiences (APX)](https://accessible.games/accessible-player-experiences/) 是 AbleGamers 的 22 条设计模式，分 Access（进得去）与 Challenge（玩得下去），用来找障碍和讨论方案，不是终检表。三套目的、粒度和作者不同，不能互相替换。

### 表单、空态、命令面板

表单先用原生控件兑现承诺，再补 ARIA。[APG Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)：输入框 + 弹出层（listbox / grid / tree / dialog），默认收起；可编辑与仅选择是两套行为。[`:user-invalid`](https://developer.mozilla.org/en-US/docs/Web/CSS/:user-invalid)（Baseline，约 2023-11 起跨引擎）只在用户交互或提交之后标无效，避免空必填一进页就全红。字段错要贴在字段旁并保持到改对；这是输入帮助，不是系统广播。

空态：[NN/g](https://www.nngroup.com/articles/empty-state-interface-design/) 要空容器说明系统状态、给学习线索、给关键任务入口；空白或「还在加载却写没有记录」会毁信任。通知：[NN/g 的 Indicators / Validations / Notifications](https://www.nngroup.com/articles/indicators-validations-notifications/) 主张 Toast 适合被动通知，**不适合**校验或字段错（会在用户改错前消失）。[Carbon Notification](https://carbondesignsystem.com/components/notification/usage/) 把 Toast 写成可超时的短消息，默认可常驻，也可编成约 5 秒后消失，并要求超时后别处还能再读；带操作的 Toast 应等到用户关掉。两边都留，不要并成一条家规。

命令面板：APG **没有** Command Palette 专模。行业实现叠 [Dialog (Modal)](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)（焦点困在层内，Escape 关，关闭后焦点回唤起处）+ [Listbox](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/)（选项、键盘与 type-ahead）。[cmdk](https://github.com/pacocoursey/cmdk) 是 React 组合库，不是 W3C 模式。

## 例子

- 正例：必填邮箱用原生 `type="email"` + 可见标签；用 `:user-invalid` 在用户改过或提交后再标红；错误文本写在字段旁并用 `aria-describedby` 挂上。
- 正例：空收藏夹写「还没有收藏」+「去加一条」按钮，不留白，也不在请求未完成时写「没有记录」。
- 正例：快捷命令打开模态对话框，选项走 listbox，Escape 关闭并把焦点还给唤起控件。
- 反例：用 `role="button"` 的 `div` 却不提供键盘激活（APG：角色是承诺）。
- 反例：把 COGA Note 或 XAG 勾完，写成「已符合 WCAG」或「已满足无障碍法规」。
- 反例：字段校验只弹 Toast；或把 cmdk 的外观当成 APG 专模。

## 边界与易混概念

- 本页不是角色卡皮肤、不是「已采用」的组件库，也不搬 WCAG / APG / COGA 全文。
- 视觉对比度、减少动效见 [[concepts/视觉CSS与设计token]] 的「无障碍底线」；本页管合同分层与控件模式。
- APG ≠ WAI-ARIA 规范 ≠ WCAG。ARIA 给语义，APG 给用法，WCAG 给符合性。
- 包容设计方法 ≠ 通用设计「一份适配所有人」≠ WCAG 符合性声明。
- Plain Language ≠ Easy Read ≠ COGA 目标/模式。
- GAG 分档 ≠ XAG 护栏 ≠ APX 模式语言；XAG 自己否认法律清单身份。
- Toast ≠ 字段校验；Inline / Callout / Modal 各管不同打断级别（Carbon 四分法）。
- 命令面板 ≠ Combobox 专模；无 APG 专条时是 Dialog+Listbox 的叠用。
- Easy Checks 迁址空壳、未核过的读屏版本，不当现行验收真源。
- 不写攻击或绕过辅助技术；不搬卡 JSON；不做成品皮肤。

## 必须保留的冲突

下列冲突不得静默合并。检索日 2026-08-14，账本见 [[queries/第二批蒸馏目标]]、[[queries/第三批蒸馏目标]]。

1. **APG 是模式指南，不是规范；WCAG 2.2 才是 Rec。** 跟 APG 示例不能当成符合性证明。
2. **包容设计 ≠ 无障碍 ≠ 通用设计。** 方法、可测标准和「一份设计服务所有人」是三层。
3. **COGA Note 不构成 WCAG 符合性。** Content Usable 与补充模式是超出现行成功标准的指导。
4. **Plain Language ≠ Easy Read ≠ COGA。** 联邦简明语言、配图易读版、认知任务组目标不可互换。
5. **GAG / XAG / APX 三轴不可互换；XAG 不是法律合规清单。** XAG v3.2 正文自己这样写。
6. **NN/g 主张字段错勿用 Toast，Carbon 允许 Toast 超时。** 两边都留：字段错贴字段；系统短消息可否超时，按产品合同选，不要假装行业已统一。
7. **命令面板：APG 无专模，叠 Dialog+Listbox。** cmdk 等库是实现，不是缺失的那条 APG 模式。

## 映射到本仓库

先按行业合同看三块界面，不按「卡能不能用」删方案。

**HUD / 覆盖层。** 悬浮球、抽屉、浮窗是入口外壳，内容仍在控制中心或状态栏。覆盖层要按 Dialog 管焦点：打开时焦点进层，Tab 不漏到背后，关掉后还回去。跨文档 iframe 是独立浏览上下文，框内焦点与读屏树到不了父页；认窗见 [[concepts/酒馆宿主与iframe分层]]。半透明玻璃和细字的对比度、大位移动效可关，只链 [[concepts/视觉CSS与设计token]]，不在本页重写。

**表单。** 设置项、筛选、向导都是表单：可见标签、`:user-invalid`、字段旁持久错误。Combobox 不要做成「看起来像搜索、读屏却是一堆无角色的 div」。字段错走字段，不走会消失的角标。

**空态。** 无收藏、无日志、无筛选结果，要写清「空 / 还在加载 / 出错」，并给下一步。不要用加载中的「没有记录」骗走用户。

角色卡只在这里点名、不当过滤器：开局向导和授予者表是表单；控制中心设置是表单；状态栏空分页是空态；若做命令面板，按 Dialog+Listbox 叠，不发明 APG 专模。细则见 [[concepts/开局页路径]]、[[concepts/控制中心与状态栏]]、[[concepts/入口外壳与HUD宿主]]。
