# 后端架构名词与工坊对照

后端名词先判断规模、团队和一致性要求，再决定付不付分布式税。本页按行业合同写。工坊只是其中一条产品映射，见文末；产品禁令表见 [[comparisons/工坊架构该上与不该上]]。行业总表见 [[comparisons/行业架构方案何时用]]。

Gateway token、OAuth 密钥、对象存储凭证不进本 Vault。

## 小应用网关不是微服务 API Gateway

「Gateway」在行业里常指门后一排服务的路由/鉴权/限流。一个同进程小应用服务管生命周期、所有权和审核，不是那种门。听成「已经微服务」，或因此要上 distributed monolith，都是用错词。Azure 的 [gateway routing](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-routing) 与 [Newman BFF](https://samnewman.io/patterns/architectural/bff/) 是两种不同的门。

## 部署形态

| 名词 | 优点 | 缺点 | 代价 |
|---|---|---|---|
| 模块化单体 | 事务简单、一条栈、部署一次、边界可后抽 | 边界靠纪律；扩缩只能整包 | 架构测试/包可见性，不是零成本微服务 |
| 微服务 | 独立扩缩、团队自治、故障隔离（做对时） | 分布式事务、观测、版本、运维税 | 复杂度不够就净亏 |
| Modulith | 先强制模块，再按需抽服务 | 名字让人以为已经分布式 | 真拆进程立刻付网络税 |

英文里 Modulith 几乎等于模块化单体，不是第三种分布式风格。来源：[Monolith First](https://martinfowler.com/bliki/MonolithFirst.html)、[Microservice Premium](https://martinfowler.com/bliki/MicroservicePremium.html)、[Microservices](https://martinfowler.com/articles/microservices.html)、[Spring Modulith](https://docs.spring.io/spring-modulith/reference/index.html)。

微服务该上的条件是独立扩缩/发布的收益大于溢价，不是「以后可能很大」。Modulith 先强制模块，真拆进程立刻付网络税。

## 怎么切核心

|  | 怎么切 | 依赖 | 一句话差 |
|---|---|---|---|
| 三层 | UI → 业务 → 数据 | 从上往下，领域常绑 ORM | 好上手；横切变更贵 |
| 六边形 | 核心 + 端口/适配器 | 外依内；UI 与 DB 对称 | 核心可无 UI/DB 测 |
| 整洁 | 实体→用例→适配器→框架 | 只许朝内 | 比六边形多显式用例圈 |

三层按技术分层；后两者按依赖倒置保护核心。系统变大后应按业务模块切，模块内部再分层，不要永远三大包。小服务用模块 + 所有权边界即可，别先上四层项目。

来源：[Fowler layering](https://martinfowler.com/bliki/PresentationDomainDataLayering.html)、[Hexagonal](https://alistair.cockburn.us/hexagonal-architecture)、[Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)。

## 写读分离与事件

**CQRS**：写模型与读模型分开，可以没有事件。读写不对称、读侧要单独扩或单独优化时该上。多数 CRUD 是高风险复杂度。来源：[Fowler CQRS](https://martinfowler.com/bliki/CQRS.html)。

**事件溯源**：状态由不可变事件序列重建。审计、重放、时间旅行强；版本与查询都难。常和 CQRS 组合，**不绑定**。来源：[Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)。

对称的包 CRUD + 状态机不必上双模型。这不是「CQRS 不存在」。

## Saga 三义

「Saga」不是一词：microservices.io 的数据模式、Temporal 工作流里的补偿代码栈、BPMN 2.0.2 的补偿事件，三框不同义。详页见 [[concepts/Saga三义与补偿]]。

Inbox 的正式名是 Idempotent Consumer。Fowler 无 Saga / Outbox 专文。熔断 / 舱壁 / 重试不并进本词。

来源：[Richardson Saga](https://microservices.io/patterns/data/saga.html)、[Temporal Saga](https://docs.temporal.io/design-patterns/saga-pattern)、[OMG BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/)。

## 怎么说话

| 名词 | 一句话 | 何时用 |
|---|---|---|
| 同步 REST | 现在就要答案 | 发布 / 审核 / 详情 / 大多数 CRUD |
| 消息队列 | 分活、削峰、一个消费者 | 后加通知、导出、邮件；不当同步 API 替身 |
| 事件总线 | 广播事实、发布者不认订阅者 | 扇出；主路径要同步可见时不该当骨架 |
| API Gateway | 多后端的一扇门 | 后面没有一排服务时过重 |
| BFF | 一个 UI 一个后端 | 多客户端形状差很多时该上；只有一个客户端时不必再套 |

来源：[Sam Newman BFF](https://samnewman.io/patterns/architectural/bff/)、[Azure BFF](https://learn.microsoft.com/en-us/azure/architecture/patterns/backends-for-frontends)、[Gateway routing](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-routing)、[Pub/Sub](https://learn.microsoft.com/en-us/azure/architecture/patterns/publisher-subscriber)。模式总表：[Azure Cloud Design Patterns](https://learn.microsoft.com/en-us/azure/architecture/patterns/)。

## 限流 ≠ 节流 ≠ 令牌桶

微软 Azure 架构中心把三件事分开写，不能并成一个「限流算法」。

| 词 | 谁做 | 管什么 |
|---|---|---|
| Rate Limiting（限流） | 调用方 | 控制自己发出请求的速率，以免撞上对方的节流上限 |
| Throttling（节流） | 被调用方 / 工作负载 | 封顶资源消耗，负荷下仍保 SLO |
| Token bucket（令牌桶） | 一种计量算法 | 桶容量 + 补充速率；节流页里与漏桶、固定窗、滑动窗并列 |

来源：[Rate Limiting](https://learn.microsoft.com/en-us/azure/architecture/patterns/rate-limiting-pattern)、[Throttling](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling)。

## 十二因素与 CAP

[12factor.net](https://12factor.net/) 现网仍是 2011 年 Adam Wiggins 正文。2024-11 起社区修订仓是 [twelve-factor/twelve-factor](https://github.com/twelve-factor/twelve-factor)，默认枝 `next`，**尚未**替换现网站。

Brewer 2012 把 CAP「三选二」标为误导：分区少见时不必先放弃 C 或 A；选择可以按操作、数据、子系统细分。CAP 只禁止分区存在时同时要完美的 C 和 A。Gilbert/Lynch 2002 证明文无合法免费全文，本页不链盗版。

来源：[Twelve-Factor](https://12factor.net/)、[修订仓](https://github.com/twelve-factor/twelve-factor)、[CAP Twelve Years Later](https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/)。

## JS Temporal 未进现行 ECMA-262

这是 ECMAScript 日期时间 API，**不是** Temporal.io 工作流引擎。提案已 Stage 4（TC39 2026-03）。活稿仍在 [proposal-temporal](https://tc39.es/proposal-temporal/)。并入 [ECMA-262 PR #3759](https://github.com/tc39/ecma262/pull/3759) 截至 2026-08-13 仍开。外文「已经进 ES2026」在并入 PR 合入前不可信。

Cookie 管浏览器会话；JWT 管声明信封；OAuth 管谁来证明人。三件可叠，不是三选一。

## Auth 三件不是三选一

| 名词 | 管什么 | 优点 | 坑 |
|---|---|---|---|
| Session Cookie | 浏览器会话 | 可立刻作废；HttpOnly 时 JS 偷不到 | CSRF；要存会话 |
| JWT | 声明信封 | 服务间传声明、少查库 | 难提前作废；别当无状态浏览器会话 |
| OAuth 委托 | 谁来证明人 | 不存密码；发布者可伪匿名 | 回调 / state 是攻击面；OAuth ≠ 授权模型 |

来源：[OWASP session](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)、[OWASP JWT](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)、[OWASP OAuth2](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html)。安全验收清单用 [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)，不是攻击手册。

业界常见把 JWT 塞 `localStorage` 当登录态；[OWASP JWT](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html) 不赞成。本页两边都留：会话建议跟 OWASP，JWT 仍正当用于服务间声明。

## 契约一句

|  | 取舍 |
|---|---|
| OpenAPI | 跨语言 HTTP 合同。公共 API 合适。要生成客户端再补文件。 |
| tRPC | 单一 TS 仓、前后端一起改时爽。离开 TS 或要对外文档就痛。 |
| GraphQL | 多客户端要自选字段、少 over-fetch 时该上。N+1、授权、缓存都更难，不是 REST 的默认升级。详钉见 [[concepts/GraphQL与异步事件合同]]。 |

## HTTP 问题详情与幂等键

RFC 9457（2023-07）废止 RFC 7807，是现行 HTTP API 问题详情。媒体类型仍是 `application/problem+json` / `application/problem+xml`。字段、协商和类型 URI 见 [[concepts/HTTP合同与问题详情]]。

IETF `Idempotency-Key` 草案 `draft-ietf-httpapi-idempotency-key-header-07` 已于 2026-04-18 过期，IESG 标 Expired，暂无继任 RFC。

来源：[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)、[幂等键草案 datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)。

## 工坊已经在用（对照）

| 名词 | 工坊怎么落 |
|---|---|
| 模块化单体 | Gateway 同进程：包生命周期 + 所有权 + 审核 API |
| 静态站 + 对象存储 + 小写面 | 目录 / schema / 索引静态；包文件进存储；Gateway 只管写与鉴权 |
| OAuth 委托 | 证明发布者，伪匿名；不是玩家追踪 |
| 同步 REST | list / detail / create / update / withdraw / review |
| 审核状态机 | pending → approved / rejected / withdrawn |
| 弱多租户 | 多发布者共享一套目录，隔离靠所有权 |

详细 schema 以工作区 `rolecard-diy-workshop/schemas/` 为准，本页不复制。卡内 fail closed 见 [[concepts/创意工坊与安全契约]]。

## 例子

- 正例：读写对称的包服务用模块化单体 + 同步 REST；读侧要单独扩再考虑 CQRS。
- 正例：浏览器会话用 Cookie；资源服务器之间传 JWT 声明。
- 反例：为「以后可能很大」先拆微服务；用事件总线冒充同步审核结果。
- 反例：把「工坊现在不上」写成「GraphQL / CQRS 不是正当方案」。

## 边界与易混概念

- 本页文件名带「工坊对照」，正文以行业名词为主；工坊落点见「工坊已经在用」与文末映射。
- API Gateway ≠ BFF ≠ 同进程小应用网关。
- CQRS ≠ 事件溯源。
- OAuth ≠ 授权模型。
- RFC 7807 已被 9457 废止；问题详情字段见 [[concepts/HTTP合同与问题详情]]。
- 「Saga」三义不可并成一词；详页 [[concepts/Saga三义与补偿]]。
- 微软限流 ≠ 节流 ≠ 令牌桶。
- CAP「三选二」已被 Brewer 2012 标为误导；十二因素现网仍是 2011。
- JS Temporal Stage 4 ≠ 已写入现行 ECMA-262。
- `Idempotency-Key` 草案 -07 已过期，暂无继任 RFC。

## 映射到本仓库

当前工坊：Gateway 同进程管包生命周期 + 所有权 + 审核；目录静态；包进对象存储；同步 REST（list / detail / create / update / withdraw / review）；状态机 `pending → approved / rejected / withdrawn`；OAuth 只证明发布者；弱多租户靠所有权。卡内 fail closed 见 [[concepts/创意工坊与安全契约]]。
这是产品落点，不是对微服务 / CQRS / GraphQL / 队列的行业否定。
RFC 9457、Saga、限流算法、十二因素修订、JS Temporal 都是行业句，不是工坊已采用清单。发布/审核主路径不必先上问题详情信封、跨服务 Saga 或令牌桶。
