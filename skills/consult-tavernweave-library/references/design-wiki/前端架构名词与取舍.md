# 前端架构名词与取舍

前端架构先回答三件事：页面怎么切、HTML 在哪生成、状态放哪。名词本身没有对错；对错在规模、团队和交互密度对不上。本页按行业合同蒸馏，不按「角色卡能不能用」删方案。对照表见 [[comparisons/行业架构方案何时用]]。动效库见 [[concepts/动画库与动效管线]]。视觉 / token 见 [[concepts/视觉CSS与设计token]]。链接账本见 [[queries/前端视觉与灵感站点蒸馏目标]]。

本仓库两条产品线的**映射**放最后一节，不当过滤器。

## 页面形态

| 名词 | 何时用 | 优点 | 缺点 |
|---|---|---|---|
| MPA | 内容站、文档、SEO、跨页状态弱 | 首屏快、可少 JS、CDN 简单 | 跨页状态丢、难做应用感 |
| SPA | 后台、编辑器、邮箱类 | 交互连续、状态可留内存 | 首包重、TTI 差、不适合内容站 |
| MPA + Islands | 内容为主、局部要交互 | 默认零 JS、按可见性注水 | 岛间共享状态要另接；堆多了变伪 SPA |
| HTMX / HDA | 服务器已能出 HTML，交互是增强 | 少前端状态机 | 复杂客户端编排弱 |

另有 [HTMX 超媒体驱动](https://htmx.org/essays/hypermedia-driven-applications/)：服务器继续出 HTML，浏览器只做增强。适合交互是「增强表单/片段」而不是重写整个客户端。复杂手势和离线编辑仍会回到 SPA。

来源：Astro [why](https://docs.astro.build/en/concepts/why-astro/)、[islands](https://docs.astro.build/en/concepts/islands/)。

## 渲染与启动

| 名词 | 何时用 | 优点 | 缺点 |
|---|---|---|---|
| CSR | 壳先出、数据客户端拉；SEO 不重要 | 可部署成静态文件 | 首屏空、爬虫弱 |
| SSR | 首屏/SEO，内容随请求变 | FCP 好、爬虫可见 | TTFB 绑服务器；全量注水仍晚可点 |
| SSG | 文档、营销、不随用户变的目录 | CDN 友好、无运行时渲染税 | 内容变要重建；个性化弱 |
| ISR | 大量内容页、可短暂滞后 | 不必全站重建 | 有陈旧窗口；静态导出不支持 |
| Hydration | SSR/SSG 之后还要交互 | 先看见再可点 | 注水前点击无效；全页注水伤 TTI |
| Resumability | 要交互但不想启动即跑全应用 | 无强制启动注水、按交互懒加载 | 与现有框架心智不兼容，生态窄 |
| RSC | React 树默认在服务端算 | 少把数据序列化给客户端 | 只在 React 栈；要学序列化边界 |

来源：[web.dev rendering](https://web.dev/articles/rendering-on-the-web)、[Next ISR](https://nextjs.org/docs/app/guides/incremental-static-regeneration)、[Qwik resumable](https://qwik.dev/docs/concepts/resumable/)。性能合同先读 [Web Vitals](https://web.dev/articles/vitals)（LCP / INP / CLS）。React 前后端分层见 [Server Components](https://react.dev/reference/rsc/server-components) 与 [Server and Client](https://nextjs.org/docs/app/getting-started/server-and-client-components)。RSC 是 React 树的默认服务端计算，不是「又一种 SSG」。

## 微前端、联邦、BFF

| 名词 | 何时用 | 优点 | 缺点 |
|---|---|---|---|
| 微前端 | 多团队、独立发布、前端单体已堵交付 | 团队自治、可分期上线 | 一致性、共享依赖、非原子发布；小团队常亏 |
| Module Federation | 已决定微前端，要运行时拼装 | 独立部署、少重复打包 | 版本错配、调试难、运行时失败面大 |
| Web Components 微前端 | 技术栈无关嵌入，主要隔离样式 | 浏览器原生、容器薄 | 不是源隔离；无障碍/SSR 要另做 |
| BFF | Web / 移动 / 嵌入要的数据形状差很多 | 少 round-trip、契约跟 UI 走 | BFF 增殖；代管会重新变瓶颈 |

来源：[Fowler micro-frontends](https://martinfowler.com/articles/micro-frontends.html)、[Module Federation](https://webpack.js.org/concepts/module-federation/)、[Sam Newman BFF](https://samnewman.io/patterns/architectural/bff/)。Fowler 没有独立 BFF bliki，BFF 用 Newman 原文。

联邦是运行时、可独立部署的拼装。单体仓是构建时共享源码与工具链。只要更快构建、不要独立发布，用单体仓。只有发布节奏必须错开才上联邦。来源：[Nx micro-frontend](https://nx.dev/docs/technologies/module-federation/concepts/micro-frontend-architecture)。

BFF 与 API Gateway 不是同一种门，见 [[concepts/后端架构名词与工坊对照]]。

## 状态分层

| 名词 | 放什么 | 不要放什么 |
|---|---|---|
| 本地 UI state | 开关、输入草稿、当前 tab、拖拽 | 别人会改、刷新必须还在的数据 |
| 服务端状态 / Query | 列表、详情、权限、MVU 快照 | modal 开合、纯 UI 开关 |
| 全局 store | 跨应用共享且更新逻辑复杂的客户端真相 | 每一个输入框的值 |

来源：[Redux organizing state](https://redux.js.org/faq/organizing-state)、[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview)。

URL 也可以当状态（筛选、页码、深链）。该进 URL 的不要只放内存。

## 样式架构

| 名词 | 何时用 | 优点 | 缺点 |
|---|---|---|---|
| 组件驱动 | 同一控件多处、多主题 | 可单独测、设计与实现同契约 | 没有 token 会变成组件坟场 |
| 工具类 CSS | 应用 UI、要快、有组件封装重复组合 | 无全局级联战争 | 标记噪；嵌入宿主容易漏进主文档 |
| 语义 CSS / BEM | 嵌入宿主、选择器必须可审计 | 可读、特异性低 | 要命名纪律；易长出巨型 CSS |
| Design tokens | 站点 / HUD / 管理台要同一套决策 | 主题可替换，组件不写死魔法数 | 只贴 token 文件、组件仍写死色值，系统是空的 |

来源：[NN/g design systems](https://www.nngroup.com/articles/design-systems-101/)、[W3C Design Tokens CG-FINAL 2025-10-28](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/)、[BEM](https://bem.info/en/methodology/)、[Tailwind utilities](https://tailwindcss.com/docs/styling-with-utility-classes)。DTCG 是社区组报告，不是 W3C Recommendation。

嵌入别人的文档时，utility 容易漏进宿主；BEM 或 `data-*` 更好审计。独立站点可以 utility + token 并行。细则见 [[concepts/视觉CSS与设计token]]。

## 嵌入边界（摘要）

三路径对照见 [[comparisons/嵌入三路径对照]]。一句话：

- **iframe**：独立浏览上下文。不信任第三方、要源隔离时用。`allow-scripts` + `allow-same-origin` 会自我解除沙箱。来源：[sandboxed iframes](https://web.dev/articles/sandboxed-iframes)。
- **同文档挂载**：共享事件循环和焦点，能摸输入框和主题变量。无源隔离，样式会互撞。
- **Shadow DOM**：封装 DOM/CSS。和宿主同 JS 堆、同卡顿。来源：[Using shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)。

跨文档 iframe 的 `backdrop-filter` 糊不到父页。iframe 里 `1vh` = iframe 高。细则见 [[concepts/视觉CSS与设计token]]、[[comparisons/嵌入三路径对照]]。

## 实时

| 名词 | 何时用 | 优点 | 缺点 |
|---|---|---|---|
| 轮询 | 更新稀、可晚几秒 | 无状态、好缓存、断了下次自己好 | 高频浪费；延迟 = 间隔 |
| SSE | 进度、通知、直播列表（只听） | 比 WebSocket 简单，走 HTTP | 单向；HTTP/1.1 每域连接数很少 |
| WebSocket | 协作编辑、对战、在场、高频双向 | 全双工，不必为回复再拉 | 心跳、鉴权续期、代理都要自己管 |
| 乐观更新 | 低冲突、可逆的写 | 手感不受 RTT 绑死 | 钱、权限、库存不要先乐观 |

来源：[SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)、[WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)、[useOptimistic](https://react.dev/reference/react/useOptimistic)。

协作编辑、对战、在场这类产品该上 WebSocket；目录页和偶发审核不必。

## 例子

- 正例：文档站 SSG + 搜索岛；后台用 SPA；多客户端形状差很多时加 BFF。
- 正例：按钮用 CSS transition，长滚动叙事用 GSAP，见 [[concepts/动画库与动效管线]]。
- 反例：内容站一上来整站 SPA + 微前端 + 自建 WS 推静态目录。
- 反例：把「卡用不上」当成行业方案不存在。

## 边界与易混概念

- 本页不是设计系统采纳清单，也不是工坊/HUD 禁令表。
- Islands 堆多了就是伪 SPA；有岛不等于已经做对性能。
- RSC ≠ SSG；CSR ≠ SPA（SPA 是应用形态，CSR 是渲染位置）。
- BFF ≠ API Gateway。

## 映射到本仓库

角色卡 HUD：入口挂宿主 document；整页脚本走 TH iframe；开合/拖拽 = 本地 UI state；MVU = 服务端状态心智。详见 [[concepts/酒馆宿主与iframe分层]]、[[concepts/MVU变量闭环]]。
独立工坊站：当前落点是 SSG/ISR + islands + 小 Gateway，见 [[comparisons/工坊架构该上与不该上]]。
这两条映射不删除上表里的 SPA、联邦、WebSocket、GraphQL。
