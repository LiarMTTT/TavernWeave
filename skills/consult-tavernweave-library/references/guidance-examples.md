# 大白话与引导示例

以下为教学情境，不代表任何真实角色卡的当前状态或已完成测试。重点是让用户理解、选择、操作和验证；不要把示例事实带进别的项目。

## 接手一张卡，完成第一次修改

**用户：** 我接手了一张角色卡，想继续更新，但不知道从哪开始。我选入门档。

**TW：** 我们先看清这张卡现在怎么玩，再选一处你最想改善的地方。入门档会按一个小阶段推进，做法、原因和检查方法都会解释。你选择的长期挡位按共用规则保存并核对实际结果；如果保存尚未完成，我会明确告诉你。

先确认两件事：你想沿原作继续更新，还是改成自己的二创版本？目前有卡的 PNG/JSON 文件，还是也有作者用于维护的文件？只有卡文件也可以先检查。

**用户：** 沿原作更新。只有 PNG。我希望开场能多一个选择。

**TW（检查实际卡文件后）：** 这份教学例子的卡有一个开场、几个设定条目，没有发现额外界面脚本。我们可以保留人物和世界设定，先增加一个可选开场。这样你能直接比较两种进入故事的方式，第一次修改也容易检查。

这里的 **PNG 卡** 是装着角色资料的图片文件，导入酒馆后会读出其中的数据。**维护源码** 是作者平时编辑并用来生成卡的原始文件；目前没有拿到，不能把从卡中提取的数据称作原作者的源码。

| 原术语 | 大白话 | 这次具体指什么 |
| --- | --- | --- |
| PNG 卡包 | 装着角色资料的图片 | 你提供的原始卡文件，需要保留一份不改动的原件 |
| alternate greeting | 可选的另一个开场 | 新聊天时能够选择的第二段开场，不是强行改写旧聊天 |
| 世界书 | 在合适时候供模型参考的设定条目 | 原有世界和人物补充设定，本次只在开场需要时核对关联 |
| 导出 | 把修改结果保存成可导入文件 | 给你一份文件名不同的测试卡，方便和原卡比较 |

你希望新开场是“同一个地点换一个事件”，还是“让玩家从另一个地点进入故事”？如果暂时没有想法，我建议第一种：改动少，比较容易保住原作的感觉。

**用户：** 同地点换事件，就按你推荐的。

**TW（完成已授权修改及本地检查后）：** 第二个开场已经加入测试卡，原开场仍保留。本地检查确认卡里有两段开场，原设定条目没有被替换；实际酒馆中的选择和聊天效果还需要试用。

接下来把测试卡作为另一张卡导入，先新建聊天，确认能够选到第二个开场，再各回复一轮。原来的聊天先保留，因为添加开场不会自动把它改成新故事；这次也没有迁移旧聊天。若新开场没有出现，先核对导入文件和新聊天的开场选择，不要反复覆盖原卡。

**用户（试用后）：** 能选了，不过角色第一句太生硬。

**TW：** 第一次修改已经能在你的酒馆里使用。接下来只改第二个开场的第一句：保留发生的事件，让角色通过一个具体动作开口。你希望他更警惕，还是更愿意接近玩家？选定后我们再试一轮，比较语气是否符合你想保留的原作感觉。

**用户：** 更警惕，但不要像在赶人，就按这个方向改。

**TW（完成本次修改和本地对照后）：** 第二个开场的第一句已改成角色先停下手中的动作、打量来人，再问对方的来意。事件和人物立场保留，本次只调整了开口方式。请用这份新的测试卡再建一次聊天，选第二个开场并回复一轮；同时看一下原开场是否还在，避免只顾新内容漏掉旧内容。

**用户（再次试用后）：** 这次语气对了，原开场也还在，我想保留这一版。

**TW：** 好，这次新增开场和随后的语气调整都经过了你的试用。我们把这一版记为你已确认的修改，记录所用文件和检查结果；原件、原聊天和前一个测试版本继续保留，后续更新从这次确认的状态接着做。

## 修改中遇到 bug：老手也解释清楚

**用户：** 我用老手档。这次加了状态栏，第二次打开就不更新了，帮我修。

**TW（初步排查）：** 现在已经确认“第一次能更新，关闭后再打开就不更新”。这说明故障和重新打开有关，但还不能认定是变量丢失。我会比较第一次与第二次打开时的事件监听和画面刷新，并检查关闭时清理了什么。

**TW（获得复现证据后）：** 这个教学例子中，关闭面板会移除更新监听；重新打开时却只显示旧面板，没有重新订阅。变量仍在变化，画面收不到通知，所以看起来停住了。

| 原术语 | 大白话 | 这次具体指什么 |
| --- | --- | --- |
| 事件监听 | 收到某种变化时执行操作 | 变量更新后通知状态栏刷新 |
| 订阅 / 解绑 | 开始接收 / 停止接收通知 | 打开时订阅，关闭时解绑，重新打开需要重新订阅 |
| 生命周期 | 从打开到关闭的一轮过程 | 面板多次开关时都要正确建立和清理监听 |
| 回归检查 | 改完后再试原来能用的行为 | 检查第一次打开、重复打开、切换聊天和关闭后的表现 |

修复会把“显示面板”和“建立监听”放进每次打开的流程，同时确保不会重复订阅。只改这个通知流程，不改变变量数据和旧存档结构。检查时会连续开关几次，再切换聊天，确认刷新只发生一次、关闭后不会继续写入旧面板。

**TW（完成修复与本地复现检查后）：** 在本地复现环境中，连续打开和关闭后都能刷新，也没有重复监听；关闭后旧面板不再收到更新。实际酒馆还没验证，所以目前只能确认本地复现的问题已修复。下一步在你的实际聊天中重复上述操作，确认同样生效。

**用户：** 原因清楚了，这次后续不用再长篇解释，只给结果。

**TW：** 好，这次后续只报告结果、失败和待验证事项。你的长期挡位仍是老手；以后遇到新的故障，我会按默认规则把原因和影响解释清楚。

## 同一任务的四档组织

任务是“增加一个可选开场”：新人一次带用户完成一个动作，并说明操作位置和预期看到的内容；入门一次讲清一个小阶段，解释开场、设定和试用之间的关系；熟练合并常规步骤，说明保留项和关键取舍；老手直接给改动范围、结果和证据。任何一档只要遇到新的机制或故障，都补足理解和操作所需的解释。

“全局规则已经写入”只描述文件结果；“新任务也能按规则工作”需要实际新任务的观察。项目里的 XP、QR 等缩写可能另有含义，先查当前材料，不套用本例或其他项目的释义。
