## 1. 定义与边界

本文所说的“自定义 CoT”是作者写给模型的推演协议。它规定生成前要检查什么、按什么顺序判断、何时跳过模块、失败时如何降级，以及最终允许输出什么。

自定义 CoT 是模型可见的 Prompt，不是模型不可见的内部推理。作者可以设计和验收这套协议，但不能借此读取、保存或证明模型的隐藏思维过程。验收应检查输入、路由和最终行为，不要求模型展示完整推理。

以下概念必须分开：

| 概念 | 用途 | 是否属于自定义 CoT | 输出边界 |
| --- | --- | --- | --- |
| 模型不可见的内部推理 | 模型自身完成生成所需的内部处理 | 否 | 不由卡片定义，不要求展示 |
| 作者编写的自定义 CoT Prompt | 规定判断问题、顺序、跳过条件和输出检查 | 是 | 默认只输出最终正文或协议要求的结果，不输出逐步分析 |
| 正文中的角色内心活动 | 塑造角色、视角和叙事体验 | 否 | 是正文，可按文风展示 |
| MVU `<analysis>` 变量更新依据 | 解释或约束本轮为何需要更新变量 | 仅是可选更新模块 | 只服务变量更新协议，不代表完整 CoT |
| 更新模型专用分析 | 从剧情结果提取源事件、源状态和合法更新 | 是独立更新 Prompt 的一部分 | 不写剧情正文，不接收无关文风与角色表演规则 |
| 脚本计算过程 | 执行确定性公式、批量派生和数据整理 | 否 | 由代码运行，不改写成冗长自然语言推演 |

“角色在犹豫什么”可以出现在正文中；“当前事实是否足以支持角色背叛”属于行为判断；“好感度是否应更新”属于可选变量判断；“好感度加成后总值是多少”若公式确定，应由脚本计算。四者不要写进同一个步骤。

## 2. 部署位置

先判断规则的复用范围、激活条件和接收模型，再决定放置位置。

| 放置方式 | 适用场景 | 不应放入的内容 |
| --- | --- | --- |
| 预设中的通用自定义 CoT | 多张卡都需要的输入检查、场景识别、行为选择、连贯性和输出检查 | 单一卡片的人名、专属能力、固定剧情答案 |
| 角色卡中的专项补充 | 该卡独有的行为限制、叙事机制、专属判断条件 | 已由预设提供的完整通用步骤 |
| 世界书条件触发的 CoT 模块 | 仅在地点、事件、角色、战斗或系统条件成立时需要的判断 | 无条件常驻的整套主 CoT |
| 按深度或顺序注入的 CoT 片段 | 已验证运行时能够把片段稳定送到目标阶段，并且上下文位置会影响语义 | 未查证的字段名、宏、顺序值或注入 API |
| 独立剧情模型 CoT | 剧情推进、角色行为、NPC 调度、叙事输出 | 低层变量写入格式和确定性脚本公式 |
| 独立变量更新模型 Prompt | 从已生成剧情提取源事件和源状态，执行合法变量更新 | 剧情风格、角色表演、候选剧情和正文格式 |

默认采用：

```text
预设通用 CoT
  + 角色卡常驻专项增量
  + 当前条件激活的 CoT 模块
```

不要让每张卡复制一整套完整 CoT。只有在目标环境不支持可靠拼接时，才生成一份完整回退版本；完整版本应由主 CoT 和增量源合成，不应成为第二份手工维护的源。

按以下顺序做位置判断：

1. 多张卡都成立的规则放预设。
2. 只对当前卡成立、每轮都需要的规则放卡片专项增量。
3. 只在明确条件下成立的规则放条件世界书或项目已验证的条件注入层。
4. 只给剧情模型或更新模型使用的规则进入各自 Prompt，不放进共享上下文。
5. 依赖具体 SillyTavern、扩展、宏、字段、深度或顺序语义时，交给 `$sillytavern-api-reference` 查证目标版本；本文不定义这些 API。

## 3. 模块设计

### 3.1 模块契约

每个模块只解决一个明确问题。为模块记录：

- 稳定模块 ID；
- 要回答的问题；
- 所需输入；
- 判断条件；
- 产生的结论或下游输入；
- 结论是否允许出现在最终输出；
- 跳过条件；
- 信息不足或冲突时的降级方式；
- 接收模型；
- 预估 Token 成本。

这些字段是作者侧设计契约，不是 SillyTavern API 或世界书 JSON 格式。

### 3.2 可删减的通用流程

常用流程可以是：

```text
输入检查
→ 当前场景识别
→ 角色状态判断
→ 目标与冲突判断
→ 行为选择
→ 连贯性检查
→ 输出组织
```

这只是组合基线，不是所有卡片必须执行的固定七步。没有群像就删除 NPC 调度；没有战斗就删除系统判断；没有变量系统就删除 MVU 更新判断；纯格式转换任务可以只保留输入检查和输出格式检查。

### 3.3 模块库

| 模块 | 解决的问题 | 可检查条件 | 何时跳过 |
| --- | --- | --- | --- |
| 输入检查 | 本轮必须回应什么，哪些事实和约束有效 | 最近用户输入、当前场景、已确认事实、有效协议是否齐全 | 输入已由上游结构化且无歧义 |
| 当前场景识别 | 人物、地点、时间、进行中的事件是什么 | 只采用上下文已出现或规则明确给出的事实 | 与输出无关的纯格式任务 |
| 剧情判断 | 本轮应推进、维持还是收束哪条线 | 当前悬念、已发生因果、用户可行动空间 | 无剧情推进要求 |
| 角色状态判断 | 角色知道什么、想要什么、能做什么 | 已知信息、动机、关系、能力、身体与情绪状态 | 无角色行为或仅处理系统数据 |
| 目标与冲突判断 | 哪些目标兼容，哪些约束发生冲突 | 目标优先级、风险、代价、角色底线、用户行动 | 没有选择或冲突 |
| 行为选择 | 哪个行为最符合当前事实并保留后续空间 | 行为必须可由角色状态和场景支持，不提前保证结果 | 行为已由用户或确定性规则指定 |
| 群像 / NPC 调度 | 本轮谁需要行动、谁只需保持在场 | 在场性、知情范围、行动必要性、发言重复、镜头占用 | 单角色场景 |
| 战斗或系统判断 | 需要哪些语义判定，哪些交给脚本 | 行动意图、目标、前置条件、叙事结果类别、脚本所需源输入 | 没有系统事件，或结果完全由脚本给出 |
| 连贯性检查 | 是否出现越权、瞬移、失忆、重复、无因结果 | 与最近事实、角色知识、时间线和未解决事件比对 | 上游已提供经过验证的确定性结果 |
| 输出格式检查 | 最终输出是否满足正文和结构协议 | 必填区块、顺序、标签、禁止内容、只出现一次的约束 | 目标没有格式契约时仍应做最小正文检查 |
| 卡片专项 CoT | 当前卡独有规则要补充哪个阶段 | 规则只引用卡片专属差异，并声明插入阶段 | 触发条件不成立或主 CoT 已覆盖 |
| 可选 MVU 更新判断 | 本轮产生了哪些需要持久化的源事件或源状态 | 只依据已生成剧情和现有变量，不重写剧情 | 无 MVU、没有变量变化，或由独立更新模型处理 |

### 3.4 按任务组合

- 普通文字卡：输入检查 → 场景 → 角色状态 → 行为选择 → 连贯性 → 输出。
- 剧情导演：输入检查 → 场景 → 剧情目标与冲突 → NPC 调度 → 连贯性 → 输出。
- 群像卡：输入检查 → 场景 → 角色状态 → NPC 调度 → 行为选择 → 镜头与重复检查 → 输出。
- 战斗 / 系统卡：输入检查 → 前置条件 → 语义结果判断 → 脚本输入整理 → 连贯性 → 输出。
- MVU 卡：先使用适合该卡的剧情 CoT；变量更新判断作为可选后续模块，或交给独立更新模型。它不替代前面的剧情与行为判断。

## 4. 编写规范与 Token 预算

### 4.1 写成可执行判断

- 每个步骤只解决一个问题，并说明判断依据。
- 把“深入思考”“仔细分析”“全面考虑”改成可检查条件。
- 引用角色设定和世界事实，不在 CoT 中复制全文。
- 只决定本轮行动和输出组织，不提前锁死后续剧情结果。
- 示例用于说明结构或边界，不写成模型每轮都能照抄的完整答案。
- 标明哪些结论仅供判断，哪些字段或正文允许输出。
- 为每个可选模块写明跳过条件。
- 为缺失输入、规则冲突和格式修复失败写明降级策略。
- 规则无法被输出行为、结构或路由证据验收时，删除或改写。

对比：

```text
差：深入思考角色下一步应该做什么。
好：检查角色已知信息、当前目标、能力限制和已承诺事项；只选择四项都支持的行为。
```

```text
差：仔细分析战斗并计算所有结果。
好：判断行动是否成立、命中或受阻的叙事类别，并输出脚本所需的源事件；数值结算交给脚本。
```

### 4.2 判断内容与输出内容

在主 CoT 开头明确：

- 步骤名、检查表、候选行为和评分默认不输出；
- 角色内心活动只有在叙事视角和文风允许时才作为正文输出；
- 结构化结果只输出目标协议要求的字段；
- 不用“展示推理”证明协议生效；
- 格式检查只修复格式，不趁机改写已确定的剧情事实。

### 4.3 降级策略

至少覆盖：

- 缺少次要事实：使用已确认事实继续，不补写关键设定。
- 缺少决定性事实：选择可逆、低承诺的行动，或在正文中自然请求信息。
- 模块条件不成立：跳过，不输出“本模块未触发”。
- 条件模块冲突：保留主 CoT 的硬约束，停止合并冲突规则并报告作者侧冲突。
- 格式无法完整修复：保留最小有效正文；可选结构宁可省略也不伪造数据，具体协议另有硬性要求时按该协议安全失败。
- CoT 关闭、缺失或拼接失败：回到卡片稳定身份、当前事实和基本输出约束；禁用依赖该 CoT 的可选自动决策，不制造不可逆结果。

### 4.4 Token 预算与去重

先去重，再缩写。按以下顺序处理：

1. 列出预设、卡片字段、世界书、变量规则、脚本说明和输出协议中的所有模型可见规则。
2. 为关键规则分配稳定规则 ID，并指定唯一权威来源。
3. 删除语义相同但换了说法的重复规则。
4. 卡片只保留对通用规则的新增条件、例外或收紧，不重述主规则。
5. 条件模块只在需要时激活。
6. 分别统计剧情模型和更新模型实际收到的 Token，不用总文件大小代替接收方预算。
7. 用目标模型的实际 tokenizer 或运行时统计复核，不凭字符数猜测。

以下仅是开始审计时的经验范围，不是硬标准：

| 模板 | 建议起点 | 优先删减对象 |
| --- | --- | --- |
| 轻量通用 CoT | 约 150～350 个目标模型 Token | 空洞动词、重复输出提醒 |
| 角色行为与剧情 CoT | 约 300～700 个目标模型 Token | 重复角色设定、过多候选方案 |
| 复杂群像 / 系统卡 CoT | 常驻部分约 600～1200 个目标模型 Token | 未激活模块、重复角色扫描、脚本公式说明 |

复杂卡应把低频模块条件化，不应仅靠压缩措辞把全部模块永久塞进上下文。

## 5. 可直接使用的模板

以下模板是 Prompt 文本，不声明任何 SillyTavern 字段或 API。标题和分隔符可以按项目预设格式调整。部署前删除未使用的占位符与模块。

### 5.1 轻量通用 CoT

```text
自定义 CoT：轻量通用

用途：在不依赖变量系统的情况下，稳定完成当前角色与场景的下一轮回复。

执行规则：
- 下面的检查只用于组织生成。不要输出步骤名、检查表、候选答案或分析摘要。
- 只把最终正文和当前输出协议明确要求的结构交给用户。

1. 输入检查
确定用户本轮说了什么、做了什么或要求什么。区分已发生事实、角色可见信息和尚未确认的推测。

2. 场景检查
确认当前地点、在场人物、时间顺序和正在进行的事件。缺失的关键事实不要自行补成既定事实。

3. 角色检查
根据角色已经知道的信息、当前目标、关系、能力和限制选择反应。角色不得使用其不可能知道的信息。

4. 行为选择
选择一个由当前事实支持、符合角色动机、能够回应用户且不会提前锁死后续剧情的行动。若信息不足，优先选择可逆行动或自然询问。

5. 连贯性检查
检查是否与最近发生的事实冲突，是否重复上一轮，是否替用户决定未表达的想法或行动。

6. 输出检查
保持既定视角、语气和长度。除非正文风格明确需要，不展示系统判断过程。只输出最终回复。

跳过与降级：
- 没有剧情或角色行为时，可跳过第 2～4 步，只检查输入和输出。
- 某项信息缺失时，不编造关键状态；使用现有事实完成最小可靠回复。
```

这套模板可以直接用于完全没有 MVU 的文字卡。

### 5.2 角色行为与剧情 CoT

```text
自定义 CoT：角色行为与剧情

目标：让角色行为有依据，让剧情产生本轮进展，同时保留用户的行动权和后续空间。

输出边界：
- 以下判断默认不输出。
- 角色内心活动只有在当前叙事视角允许时才写成正文；它不是系统分析。
- 不输出候选行为列表、评分表或“我选择了……”之类的决策说明。

1. 读取本轮输入
提取用户明确的语言、动作、目标和限制。不要把建议、假设或未发送的选项当成已发生事实。

2. 建立当前场景
确认在场人物、空间关系、时间顺序、可用物件、正在推进的事件与尚未解决的冲突。

3. 判断角色状态
逐项检查角色的已知信息、即时目标、长期动机、情绪、关系、能力限制和已作承诺。
【卡片增量插入点：character_state.after】

4. 判断目标与冲突
确定本轮最需要回应的目标。若多个目标冲突，优先遵守明确事实、角色核心边界和用户已采取的行动，不用作者预设结局覆盖当前选择。
【卡片增量插入点：goal_conflict.after】

5. 选择本轮行为
选择能够直接回应用户、由角色状态支持并产生可感知变化的行为。重大转折必须有已出现的原因；信息不足时采用试探、延迟承诺或请求确认。
【卡片增量插入点：action_selection.after】

6. 安排剧情进展
本轮只推进当前因果链所能支持的部分。不要为追求刺激强行引入新敌人、秘密、能力或结局。保留至少一个用户可以继续介入的落点。

7. 连贯性检查
检查角色是否越过知情范围，空间和时间是否连续，情绪变化是否有触发，未解决事件是否被无故遗忘，是否重复上一轮表达。

8. 组织输出
按卡片既定视角、文风和格式写最终正文。格式修复不得改变已经确定的剧情事实。删除未替换的插入点标记。

降级：
- 卡片增量缺失时，继续执行通用步骤，不伪造专属规则。
- 场景信息不足以支持重大行动时，选择低承诺反应。
- 输出格式有可选区块但缺少可靠数据时，省略可选区块，不编造内容。
```

插入点是作者侧合并标记，不是 SillyTavern API。若项目没有自动合并器，在交付前手工合并并删除标记。

### 5.3 复杂群像 / 系统卡 CoT

```text
自定义 CoT：复杂群像与系统

目标：在多人、多事件或带规则判定的场景中，选择必要行动者，保持信息隔离，并把确定性计算交给脚本。

输出边界：
- 不输出调度表、候选方案、分数、逐步分析或脚本计算过程。
- 只输出剧情正文，以及目标协议明确要求的源事件或结构。
- 独立更新模型存在时，不在剧情正文中代写其变量更新任务。

1. 输入与有效状态
提取用户本轮动作、已确认场景事实、当前有效角色和系统状态。忽略未激活模块和过期状态。

2. 场景事件队列
列出本轮必须处理的事件，并按因果前置关系排序。只保留会改变当前回复的事件；背景事件不抢占正文。

3. 行动者筛选
对每个在场角色检查：是否知情、是否有行动能力、是否有本轮必须回应的目标、行动是否与他人重复。
只有满足至少一个明确行动理由的角色进入本轮镜头；其他角色保持在场但不强制发言。

4. 角色与 NPC 调度
先处理用户直接交互对象，再处理会改变结果的 NPC，最后处理必要的环境反应。
同一信息不让多个 NPC 依次复述。不得让未在场或不知情的 NPC 作出针对性反应。
【卡片增量插入点：npc_scheduling.after】

5. 目标与冲突
比较各行动者的即时目标、资源、风险和边界。冲突结果必须来自已知能力、当前条件和用户行动，不因预定剧情强制成功或失败。

6. 战斗或系统语义判断（仅在触发时执行）
判断行动意图、对象、前置条件是否成立，以及结果属于成功、受阻、部分达成或失败中的哪类。
只产生脚本所需的源事件和语义类别。伤害合计、资源扣减、冷却、排名、派生属性和批量联动由脚本计算。
【卡片增量插入点：system_judgement.after】

7. 剧情组织
把已选择的必要行动按因果顺序写成一个连续场景。控制镜头切换，保证用户能辨认谁在行动，并为下一轮保留可操作入口。

8. 连贯性与权限检查
检查时间、空间、知情范围、资源前置、角色能力、事件去重和用户控制权。删除无因结果和重复反应。

9. 输出格式检查
验证必填区块、顺序、标签和只允许出现一次的内容。格式错误只修复结构，不重新计算脚本结果，不新增剧情事实。

跳过与降级：
- 单角色场景跳过第 3～4 步的群像扫描。
- 无战斗或系统事件时跳过第 6 步。
- 脚本不可用时，不假装完成精确计算；按项目声明的安全回退输出语义结果或暂停该可选系统。
- 条件模块缺失时使用通用规则继续，不补写未知专属机制。
```

## 6. 预设主 CoT 与卡片增量拼接

### 6.1 主 CoT 提供稳定阶段

预设主 CoT 应提供稳定阶段 ID，例如：

```text
input_check
scene_state
character_state
goal_conflict
action_selection
continuity_check
output_format
```

项目可以删减或改名，但一个已发布的拼接契约不应随意改动 ID。卡片只声明它要补充哪个阶段，不复制阶段本身。

### 6.2 卡片声明增量

卡片增量至少声明：

- 增量 ID 和版本；
- 目标主 CoT 契约；
- 目标阶段；
- 插入到该阶段之前或之后；
- 常驻或条件激活；
- 与其他模块的先后依赖；
- 稳定规则 ID；
- 接收模型；
- 只供判断还是允许输出；
- 不支持拼接时的回退来源。

作者侧声明示例：

```text
增量 ID：card.example.behavior.v1
目标主 CoT：general-cot/v1
目标阶段：character_state
位置：after
激活：always
依赖：无
规则 ID：card.example.knowledge-limit
接收模型：plot
输出：仅供判断
规则：该角色只能依据亲历事件和已收到的报告判断幕后人物；传闻不得写成确定事实。
回退：由主 CoT v1 与本增量生成完整版本。
```

这是仓库内的作者契约示例，不是 SillyTavern 条目格式、宏或 API。

### 6.3 去重

同时做两种去重：

1. **ID 去重**：相同规则 ID 只装配一次；版本冲突时停止合并，不猜测采用哪一份。
2. **语义去重**：即使 ID 不同，只要两条规则解决同一问题且约束相同，也保留唯一权威来源。

卡片可以增加条件、例外或更窄边界。例如主 CoT 已有“角色不得使用未知信息”，卡片只需增加“该角色把未经第二来源确认的报告视为传闻”，不要再次复制通用知情规则。

### 6.4 插入位置与排序

先按主 CoT 阶段顺序装配。每个阶段内默认按以下顺序：

1. 主 CoT 的阶段规则；
2. 卡片常驻增量；
3. 当前激活的条件模块；
4. 该阶段的专项格式或交接检查。

若模块声明依赖，先满足依赖再应用默认顺序。多个条件模块仍并列时，使用项目明确的优先级；优先级相同则按稳定模块 ID 排序，保证结果可复现。不要依赖世界书当前显示顺序或偶然导入顺序解决冲突。

增量通常放在目标阶段之后，用于收紧或补充主判断。只有确实提供前置输入或前置过滤时才放在阶段之前。输出格式规则始终在内容判断完成后执行。

### 6.5 条件世界书模块的结构保护

条件模块必须：

- 只补充声明的阶段；
- 包含独立模块边界、规则 ID、激活条件和跳过条件；
- 不重新定义主 CoT 的步骤顺序；
- 不复制整套主 CoT；
- 不在正文中泄漏作者侧模块标题；
- 不把剧情模型规则送给更新模型，反之亦然；
- 在多个模块同时激活时保持可排序和可去重。

世界书的具体字段、位置、深度、顺序、关键字、绿灯、sticky 行为和目标模型可见性取决于目标运行时。使用 `$sillytavern-api-reference` 查证，不从本契约推导 API。

### 6.6 不支持拼接时的完整回退

当目标环境没有可靠拼接能力时：

1. 保留主 CoT、卡片增量和条件模块作为独立维护源。
2. 在构建或人工交付阶段按相同排序规则合成完整 CoT。
3. 把未能动态注入的条件模块改写成带明确“满足条件才执行”的可跳过段落。
4. 标记完整版本由哪些源和版本生成。
5. 静态检查未替换插入点、重复规则和模型路由。
6. 不把生成后的完整版本复制回每个增量源继续手工维护。

## 7. 与其他系统的边界

| 系统 | 与 CoT 的关系 | 边界 |
| --- | --- | --- |
| 角色卡正文 | 提供稳定身份、行为锚点和叙事内容 | CoT 引用这些事实，不复制正文；可见内心活动是正文，不是系统判断 |
| 世界书 | 提供条件知识或条件 CoT 模块 | 知识条目不因被 CoT 使用就变成 CoT；条件模块不得破坏主结构 |
| 预设 | 适合承载跨卡复用的主 CoT | 卡片只写增量；预设规则是否实际注入需按目标环境验证 |
| MVU | 提供可选持久变量与更新协议 | CoT 可以完全脱离 MVU；MVU `<analysis>` 不等于完整 CoT |
| Zod | 定义或校验结构化数据 | 与 CoT 没有直接关系；schema 不能代替行为判断，CoT 也不能代替结构校验 |
| 脚本计算 | 处理确定性公式、派生变量和批量更新 | 不把计算过程写成冗长 CoT；CoT 只提供脚本需要的语义判断或源输入 |
| 正则 | 转换、隐藏或展示已有文本 | 不负责推演，不用正则掩盖错误的 CoT 或变量协议 |
| UI | 展示状态、收集选择和触发已定义流程 | UI 不证明 CoT 已路由，也不应偷偷成为第二套判断源 |
| 额外更新模型 | 独立读取剧情结果并写变量更新 | 只接收更新所需状态、规则和格式；不接收剧情 CoT、文风和 NPC 调度 |

剧情模型和更新模型必须按职责隔离：

- plot model 接收剧情、角色行为、NPC 调度和正文输出所需的 CoT；
- update model 接收当前变量、已生成剧情、更新判断、合法操作和更新输出格式；
- 两者都需要的事实才进入共享上下文；
- 不为了“兼容”把两套 Prompt 全部发给两个模型。

## 8. MVU 与脚本计算分工

本节只讨论工作量和写入职责，不讨论玩法平衡。

基本规则：

- 语义判断交给 LLM，例如意图、关系变化原因、事件是否成立、结果类别。
- 确定性计算交给脚本，例如公式、累计、派生字段、批量同步、上限和下限。
- LLM 尽量只写源事件或源状态。
- 脚本根据源数据批量更新派生变量。
- 同一个变量只能有一个写入所有者，不能由 LLM 和脚本竞争写入。
- 合理使用脚本可以显著减少 JSONPatch 数量和 LLM 输出压力。

示例：

| 数据 | 推荐写入者 | 原因 |
| --- | --- | --- |
| `事件：角色 A 成功救援角色 B` | LLM | 需要理解剧情语义 |
| `关系变化原因：获救且确认对方承担风险` | LLM | 需要语境判断 |
| `好感基础增量、等级阈值、称号联动` | 脚本 | 公式和派生关系确定 |
| `攻击是否被叙事条件阻止` | LLM | 依赖场景和前置条件 |
| `伤害合计、生命值、资源扣减、冷却` | 脚本 | 可重复的确定性计算 |

以下经验范围不是硬标准，比例指“最终变量变化中，需要 LLM 显式输出的比例”：

| 卡片类型 | LLM 显式更新比例 |
| --- | --- |
| 轻量叙事卡 | 70%～100% |
| 混合系统卡 | 30%～50% |
| 重计算系统卡 | 10%～30% |

比例不决定卡片质量。判断依据是数据是否需要理解自然语言语义，以及计算是否可以由确定性代码可靠复现。

若使用额外更新模型：

1. plot model 只完成剧情与行为输出。
2. update model 从已生成剧情提取源事件和源状态。
3. 脚本读取这些源数据并计算派生字段。
4. 对每个变量记录唯一写入者。
5. 分别验收剧情、更新 Prompt 和脚本，不把三者串成一段长 CoT。

## 9. 验证与反例

### 9.1 静态检查

- CoT 能否在完全没有 MVU 的文字卡中使用？
- 是否默认支持缝入预设自定义 CoT？
- 是否错误复制了一整套预设已有规则？
- 卡片专项 CoT 是否只包含增量？
- 每个步骤是否有明确问题、输入和作用？
- 是否存在“深入思考”“仔细分析”一类空洞步骤？
- 是否重复正文、角色设定或世界书？
- 是否把角色内心活动当作系统判断？
- 是否把 MVU `<analysis>` 当作完整 CoT？
- plot model 和 update model 是否收到错误内容？
- 是否让 LLM 计算本应由脚本处理的确定性结果？
- 同一个变量是否被 LLM 和脚本同时写入？
- 多个条件模块能否稳定排序和去重？
- 条件模块是否会改写主 CoT 结构？
- CoT 关闭、缺失或拼接失败时是否有安全降级？
- 是否残留插入点、占位符、作者注释或完整推理输出要求？

### 9.2 反例

| 反例 | 问题 | 修正 |
| --- | --- | --- |
| “请深入思考并给出最佳剧情。” | 没有判断条件，无法验收 | 指定当前事实、角色目标、限制和可逆性检查 |
| 每张卡都复制同一套七步 CoT | 重复、易漂移、Token 浪费 | 主 CoT 放预设，卡片只写增量 |
| 世界书触发条目重新定义全部步骤 | 可能破坏主结构和排序 | 只声明目标阶段、规则 ID 和跳过条件 |
| 要求输出角色内心活动证明 CoT 生效 | 混淆叙事与系统判断 | 按文风决定是否写内心，协议靠行为和结构验收 |
| 把 MVU `<analysis>` 写成剧情、NPC、战斗和格式总控 | 职责过载且无法脱离 MVU | 剧情 CoT 独立，更新判断仅处理变量 |
| 让 LLM 逐项计算生命、资源、冷却和派生等级 | 输出长且容易算错 | LLM 写源事件，脚本批量计算 |
| plot model 和 update model 接收相同完整 Prompt | 泄漏职责并浪费上下文 | 建立接收方清单，只共享双方确实需要的事实 |
| CoT 缺失时仍强制输出依赖其判断的结构 | 容易伪造数据或崩坏 | 声明最小正文回退并禁用可选自动决策 |

### 9.3 本地静态验收

至少构造以下样例并检查生成的最终 Prompt：

1. 完全没有 MVU 的文字卡使用轻量通用 CoT。
2. 已有预设主 CoT 加载一个角色卡常驻增量。
3. 两个条件模块同时激活，排序和去重结果稳定。
4. 群像卡只让必要 NPC 行动，不让所有 NPC 轮流发言。
5. MVU 卡的剧情 CoT 与更新判断分离。
6. 额外更新模型不接收剧情文风、候选剧情或 NPC 调度。
7. LLM 只产生源事件，脚本拥有派生变量。
8. 关闭主 CoT 或移除卡片增量后仍能安全输出最小正文。

### 9.4 真实 SillyTavern 验收

静态文档不能证明实际注入顺序、世界书激活、模型接收方、额外更新模型上下文或脚本生命周期。真实验收应：

1. 记录目标 SillyTavern、扩展、预设和 MVU 版本。
2. 用 `$sillytavern-api-reference` 查证版本敏感的字段、注入、路由和可见性。
3. 用 `$sillytavern-runtime-debug` 在目标会话中取得实际 Prompt、激活条目、模型接收方和输出证据。
4. 分别测试无 MVU 文字卡、预设加卡片增量、条件模块开关、群像调度、CoT 关闭回退。
5. 若有额外更新模型，分别检查 plot 与 update 上下文，确认没有交叉泄漏。
6. 若有脚本，比较源事件、脚本计算结果、重复执行和失败回退，确认没有双写。
7. 记录 Token 变化、格式失败、重复规则和长对话后的行为漂移。

离线 Prompt 拼接、Markdown 检查或单次生成不能关闭真实运行时验收门。
