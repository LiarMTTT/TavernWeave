# 履历保存中断后的恢复

本说明只适用于 `save-mirror-record.mjs` 管理的本地追加履历。恢复沿用本次已授权保存的目录和记录；不重写旧节点，也不补造缺失的历史。

## 正常保存

保存器先取得 `.mirror-save.lock`，再读取现有链。第二个进程在锁释放前不能保存或恢复。

新节点写入 `.mirror-transaction/node/`，三个文件落盘后才生成完整的 `journal.json`。事务记录保存旧指针的原始字节及下一节点的索引。随后发布节点，依次原子替换 `index.json` 与 `latest.json`，完整复核后删除事务区并释放锁。

每个节点仍是 `record.json`、`report.html` 和 `assessment.md`；旧版不含文字评估文件的节点按原格式校验。未修改正式历史的目录结构或评分含义。

## 保存报错但进程正常退出

读取报错后，在同一目录运行：

```bash
node scripts/save-mirror-record.mjs --root <履历根目录> --recover
```

- 尚未形成完整事务记录：确认原历史仍有效后，只清理不完整暂存；随后可重新保存原草稿。
- 完整事务记录已生成：检查旧链、新节点的哈希，以及实际指针是否仍为该事务的旧值或新值；通过后完成同一次追加。
- 指针被其他操作改变、旧节点损坏、出现无关游离节点或暂存哈希不符：拒绝恢复并保留材料，不能把异常当作空历史。
- 事务已完成：返回 `no-pending-transaction`，不会再追加一次。

恢复中再次遇到普通 I/O 错误时，已完成步骤仍由事务记录识别，可以重试同一恢复命令。

## 保存进程异常终止并留下锁

检查 `.mirror-save.lock/owner.json` 中的主机名、进程 ID 和 `token`。只在同一主机确认原进程已退出后，将该锁标识传入：

```bash
node scripts/save-mirror-record.mjs --root <履历根目录> --recover --stale-lock-token <owner.json中的token>
```

保存器再次核对标识及进程是否存活，活动进程或标识不符时拒绝释放。恢复期间另有 `.mirror-recovery.lock` 阻止并发抢占。PID 被新进程复用时会保守拒绝，不能据此终止无关进程。

锁元数据缺失或损坏、主机不一致，以及恢复进程自身异常终止留下恢复锁时，不做自动清理。先确认没有任何保存／恢复进程，并保留锁和事务材料供人工核对；不要递归删除履历根目录或 `records/` 来解锁。

## 检查范围

隔离临时目录测试覆盖首次保存、历史追加、各发布检查点的故障、并发竞争和保存进程异常终止。旧节点逐文件比较保持原字节。浏览器报告另行验证便携导出和键盘行为。这些结果不证明磁盘损坏或操作系统断电时一定能够自动恢复。
