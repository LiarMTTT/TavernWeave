## 1. 体量、依赖和执行纪律

采用 `blueprint-set`：本文件兼作主实施蓝图与领域索引。由于用户希望降低单人维护负担，当前保持一份实施文件，不创建空白子蓝图。设计上最多允许四个直属领域、两层深度；只有主文件无法清楚承载独立交付与验收时，才经驾驶员确认提取对应文档。

| 领域 | 边界 | 承担阶段 | 独立领域文档 |
|---|---|---|---|
| D1 宿主与 TW 接入 | 能力探测、人格与方法路由、适配和升级 | P0、P2、P6 | 未提取 |
| D2 项目与导出 | 保存、编辑日志、交接、不同内容分工、人工导出 | P1、P3、P6 | 未提取 |
| D3 创作与资料界面 | 制卡/Vibe、真实 UI 编辑器、内置库与筛选 | P2、P3 | 未提取 |
| D4 长材料任务 | 采证、token 试验、项目子 Agent、自动落库 | P4、P5 | 未提取 |

执行次序为 `设计审阅 → 按授权完成新仓准备与权威交接 → P0 → P1 → P2 → P3 → P4 → P5 → P6`。建仓步骤是 P0 的准备检查，不增加产品阶段或领域蓝图。P3 是首个可用版本，P6 才覆盖本次大更新的全部产品要求；自动转库、Vibe 方向和第二首批宿主均不能静默挪到后续。

每阶段开工前冻结输入、输出、允许修改范围、退出条件和证据位置。任务授权覆盖明确范围后，正常步骤不重复询问；新增范围、付费、安装、远程写入、Git、归档和发布按实际独立授权处理。

所有活动阶段的 `runtimePersistentBlueprintBudget = 0`。真实失败可以开启一层临时问题支线，记录触发证据、父阶段和返回位置，同时最多一条，不新增产品分母或持久蓝图。解决或确认阻塞后关闭并返回原阶段。连续修补仍不能满足相同退出条件时，先复审该路径是否值得保留，不让“稳定”变成无限调试。

## 3. P0 · 首批连接与复用验证

**输入**：总设计案、TW 1.5.0 当前源码、现有 Soul/Library 合同、原 RPN 的真实源码与历史证据入口、当前宿主版本与公开接口。

**输出**：首批支持矩阵；来源版本/哈希与依赖清单；最小连接试验；一种前端/工具层承载方案；已选仓库与权威归属的实际交接回执；尚需的安装/连接/部署选择。源码和运行证据不混成一个“可复用”勾选。

**步骤与允许修改范围**：在批准的测试目录建立最小验证工程；只为连接真实工具和真实源组件增加必要适配。先核对公开能力，再在获得相应运行授权后测试；本阶段不改旧 RPN 产品源码、不激活其旧蓝图、不更新全局规则。

| 检查 | 必须回答的问题 | 判断规则 |
|---|---|---|
| 仓库与依赖 | 已选独立新仓是否正确建立，活动权威是否完成交接，什么变化才需联动？ | 按工作区计划核对 RPN-GodHand/私有/三处路径与实际回执；神之手依赖有限 TW 合同，不继承旧 RPN 运行环境 |
| 资料与 Skill 版本 | 如何固定 Library/Picker 快照，同时避免宿主内出现两份同名 TW Skill？ | 数据按精确快照构建，实际 Skill 单一来源；组合可检测，未知/不兼容有明确表现 |
| 宿主接入 | ChatGPT/Codex 的哪个客户端/模式能发现工具、调用工具、呈现界面？ | 各自记录版本、界面呈现、工具通道、文件权限与失败表现 |
| UI 与项目连接 | 真实界面能否读一个项目对象、人工改一次并通过工具保存？ | 必须有保存后读回；截图或按钮点击不算闭环 |
| 人工独立入口 | 没有模型回复、没有活跃聊天时如何打开相同界面和工具？ | 本地启动/项目访问办法具体可运行；不能依赖模型临时托管文件 |
| 远程访问 | 首批 ChatGPT 的项目位于哪里，如何授权访问？ | localhost 不默认对远端可见；列出维护与数据流代价后选方案 |
| UI Builder 来源 | 外部源码/注册表、仓内快照和实际可抽取模块是否对齐？ | 绑定真实源码版本，定位宿主依赖；不以捏造相似页面替代 |
| RPN 版本差异 | 根 NEXT、当前 checkout、来源工作树和历史验收分别指向什么？ | 逐项登记，仅选择已定位的模块；不自动切分支或覆盖工作树 |
| 人格与任务回执 | 公开接口能否发起用户意图并确认实际 Skill 调用？ | 列出可用回执与不可观察项，不发明状态 API |
| 后台与计量 | 是否有原生子 Agent、后台执行、续跑、取消与 token 信息？ | 逐项记 supported / degraded / unavailable / unverified |

前端嵌入要测试宿主安全策略、必要资源加载、iframe/消息通道及工具调用权限。导入项目、小说和候选内容属于数据，不能通过其中的指令触发人格切换、任意写入或扩大任务。

**退出条件**：至少一个主验证宿主的可执行链明确，并为另一个首批宿主保留经核对的适配路径；能解释用户如何独立保存导出以及长任务中断如何续接。此时只可称“路线验证”，首批双宿主正式支持在 P6 验收。

**失败回退**：嵌入失败时尝试同源完整外部编辑页；如果必须重建 Agent IDE 或长期自管复杂云服务才能完成核心需求，提交实际代价与范围调整案。不能用复制文本或手工文件交换的降级演示冒充完整神之手能力。

**下一道门**：驾驶员确认主宿主、支持表面、连接/启动办法与确需依赖后进入 P1。独立仓与三处目录已选定，活动设计和新 NEXT 应按工作区计划在产品源码实施前交接；核对实际回执，不并行维护两份当前状态。编辑原则、产品方向和已选目录不重复讨论。

## 4. P1 · 项目保存、交接与人工导出

**输入**：P0 固定的工具通道、项目格式与源码边界，用户已确认的 C05–C08。

**输出**：最小项目内容模型、真实文件读写、可恢复保存、自动编辑日志、内容范围占用、版本校验、人工入口及可编辑项目包的导出/重新打开。

**允许修改范围**：共享项目工具、最小编辑界面、必要的宿主适配、相关文档和验证。复用现有编解码能力时只抽取需要的依赖；不移植整套 RPN Runtime，不新增模型管理和云同步。

**实施顺序**：

1. 定义项目身份、内容定位和格式版本，优先验证文件形式；创建、打开、保存和重新打开同一份项目。
2. 每次保存自动生成对象差异与前后版本。实际内容、有效版本和日志保持可恢复一致，写入失败保留上一个可用状态。
3. 实现分时交接：Agent 已停止该范围的写入后，人工接手；保存后 Agent 获取有关日志和最新数据。
4. 实现不同内容的分工。逻辑条目共用同一物理文件时，由工具层串行合并；做不到时保守禁止该文件并发写入。
5. 在回写前核对对象身份和读取版本；拒绝旧内容、跨项目迟到结果和已取消任务的迟到写入。
6. 提供无需模型的独立人工入口与项目包导出；在新的测试目录重新导入并继续编辑。

**退出条件**：AT01–AT07 通过相应层级检查，真实主宿主完成一次“Agent 完成本轮 → 用户改内容并保存 → Agent 读取日志接续”的交接。日志能解释差异，实际保存内容为权威；新项目包不依赖原机器路径。

**失败回退**：记录写入前后版本，恢复上一个有效项目；不清空项目以求测试通过。发生未记录的外部修改时报告并重建差异，不能丢弃外部修改。工具层不可用时提供已验证的文件备份/恢复步骤。

**证据与下一道门**：文件与恢复回归、一次真实交接记录、人工项目包及重开记录。驾驶员试用保存与接续体验后进入 P2；人工导出的“成品格式”在 P3 补全，不因项目包通过而提前宣称全部导出完成。

## 5. P2 · 人格、创作方向与内置资料

**输入**：P1 项目通道、现有 Soul/Library 源码和公开快照、用户保存的独立引导偏好。

**输出**：项目首页和两方向入口；五种 Soul 选择；真实调用结果驱动的模式状态；Library/Picker 同源嵌入或打开；按项目保存的选择清单。

**允许修改范围**：神之手入口、宿主意图与回执适配、必要的 Library 项目选择连接、测试与说明。TW 原有命令和只装 Skill 的路径保持可用；需要更改 Skill 合同时列出明确差异，不复制一套分叉人格正文。

**实施顺序**：

1. 从制卡创作/Vibe 开发进入正确方法路由，读取已有项目权威，不在方向切换时复制或转换项目。
2. 用现有模式标识实现启用、切换、关闭请求；请求中的状态与实际已加载状态分开。
3. 核对任务身份、最新请求和实际回执；处理旧回执、断开、新任务和退出。
4. 装载真实筛选页及同源脚本/样式/manifest，保持搜索、分类、过滤、详情、预览、来源、已选与 JSON 导出能力。
5. 将选择按项目保存，使用既有候选合同与快照版本；Agent 只读取所选相关资料。
6. 检查资料更新后的失效 ID、实验路线和来源边界，并保留仅使用 Skill 的安装/运行方式。

**退出条件**：AT08–AT11 通过；五种人格选择可观察，关闭有效且不取消工程任务，三席不会自动生成三个 worker；制卡/Vibe 均可进入；完整筛选能力能把选择交给正确项目。

**失败回退**：加载失败显示实际失败或待核实；不得高亮成已启用。仅复制指令的降级方式保留为可用辅助，但不会满足人格直接切换的完整验收。资料页来源不可访问时保留目录与候选，不自动替换或下载内容。

**证据与下一道门**：真实宿主的模式启停、跨任务状态边界；真实 Picker 操作与项目选择读回；既有路径回归。驾驶员确认入口和模式体验后进入 P3。

## 6. P3 · 制卡与 Vibe 首个可用版本

**输入**：P1/P2 已验证骨架、已锁定来源的 UI Builder/前端组件、各一份授权制卡/Vibe 样本。

**输出**：两条完整创作路径；真实 UI 编辑、源稿保存与预览；目标格式导出；首次试用后的二次修改成果。

**允许修改范围**：工作台视图、真实组件的最小适配、领域校验与导出、必要文档。原件保留；源稿和测试导出分离；预览可以使用假数据但必须运行实际源组件和交互。

| 路径 | 必做操作 | 交付与实际验证 |
|---|---|---|
| 制卡 | 打开原卡/维护材料 → 用户改世界书条目 → Agent 依据日志接续 → 编辑实际 UI 组件 → 保存重开 → 人工导出 | 可编辑项目包、JSON/PNG 或已冻结目标格式；载荷与引用校验；实际本次角色卡在真实酒馆验证 |
| Vibe | 打开小项目 → 用户改需求/文案 → Agent 修改独立前端内容 → 处理一次相关交接 → 预览 → 人工导出 | 可继续开发的源码包；在新位置按明确依赖打开/检查；当前运行环境中的实际功能验证 |
| UI 编辑器 | 改布局/样式/内容或已支持绑定 → 预览 → 制造一个可控编译错误 → 修复 → 保存/导出源稿和对应结果 | 真实组件身份、源稿版本、编译结果、错误后草稿保持与重开 |

人工导出从一致的已保存快照执行；如果用户继续编辑，显示导出所对应的旧快照，不把新旧资源混合。对话断开或没有模型响应时重复一次人工保存/导出，证明没有暗中依赖模型。

**退出条件**：AT12–AT15 通过；首个可用版本满足设计案第 10.2 节；两条路径都由驾驶员实际试用。试用反馈产生一项具体小改，在授权内完成后再试用一次。真实酒馆尚未做时保持该门未验，不能标记制卡交付已验收。

**失败回退**：保留源稿、旧预览和最后可用项目版本；错误的预览明确标旧，不冒充当前结果。来源模块过度耦合时回到 P0 的抽取选择，禁止用重画假 UI 取代真正编辑器。

**证据与下一道门**：绑定源稿/导出文件的版本与哈希，记录主宿主、实际产物和驾驶员试用。此阶段不意味着大更新完成；随后确定 P4 样本、计量和额度。

## 7. P4 · 资料质量与 token 小样本试验

**输入**：P3 的可用项目、全球冰封资料库3的采证方法、授权样本原文、宿主能力表、可见的用量字段。

**输出**：样本与保留样本登记、质量考题、单 Agent/子任务对照、每份合格交付物的实际用量与时间、明确的失败/返工记录、可执行的批量配置建议。

**允许修改范围**：隔离项目数据、采证/验证/索引工具、项目任务合同和试验记录。真实模型调用只在本轮材料、提供者/宿主和额度明确后执行；不因设计允许自动化而消费未授权的外部 API。

**试验设计**：

- 至少包含普通叙事、别名/多人、跨章时间或事实冲突、原文缺口四类情况；具体量按本轮资源决定。
- 保留部分样本不参与规则调节，最后用于检验结果，避免只对固定片段有效。
- A 为单 Agent 顺序处理，B 为小规模专职分工；保持原文、输出要求与验收问题一致。若宿主没有子 Agent，明确 B 未执行，不伪造并行对照。
- 将机械索引、切片、去重、格式验证交给脚本；记录模型需要的实际输入。
- 统计父任务、子任务、汇编、复核与重试；分别保留宿主可见 token、缓存子项、时长、工具调用、人工修正和未知字段。
- 先按来源支持、关键遗漏、别名、阶段、冲突与任务问题评分，再比较质量合格样本的总用量和完成时间。样本少时说明外推范围与偏差。

**必须冻结的批量合同**：本轮原文范围与指纹、输出目录、交付类型、规则版本、任务角色和范围、宿主执行方式、并发/重试上限、可执行预算、失败停止条件与通知方式。

**退出条件**：AT16、AT17 通过；样本实际有出处、能回答设计问题；试验记录可以复核；没有把未知 token 写成零，没有提前承诺节省比例。自动化价值已确定，本阶段只选择处理方案及边界。

**失败回退**：优先缩小任务、减少重复上下文或调整采证/复核方法；质量不达标时不扩大批量。没有准确计量时，报告缺口并提出可执行的批次/调用/时长限制，由驾驶员决定该边界是否足够。

**证据与下一道门**：样本输入指纹、实际结果与来源、用量台账、对照结论及预算建议。驾驶员确认一轮自动落库范围后进入 P5，正常批次不逐个审批。

## 8. P5 · 无人值守批量落库与恢复

**输入**：P4 冻结合同、同一批次识别规则、可恢复的项目工具、宿主实际提供的执行/取消能力。

**输出**：能真实启动/暂停/继续/取消的长任务；持久批次进度；问题列表；可导出的资料库结果和实际通知。

**允许修改范围**：项目级任务与批次记录、现有工具扩展、前端任务/成果页、必要宿主适配。尽量利用原生运行能力，不添加跨宿主通用 Agent Runtime 或未获准常驻服务。

**实施与验证顺序**：

1. 将 P4 合同转为有限任务单和批次队列，显示计划范围与实际执行状态。
2. 批次结果先保存并校验，再更新完成记录；重复执行同一批不会重复落库。
3. 在保存前、保存后但回执前、批次完成后分别制造中断，恢复时核对结果而非凭聊天猜测。
4. 暂停/取消在安全边界生效；已保存成果保留。人工接管同一内容时暂停相应任务，独立范围继续。
5. 检查规则/原文变化、局部缺页、事实冲突、连续失败与预算触顶；只有可独立继续的部分自动继续。
6. 在已授权真实宿主中执行一轮小规模无人值守任务；用户无需守着正常批次。分别记录离开界面、关闭会话和退出宿主实际支持到哪里。
7. 完成或需要处理时发出实际可用渠道的通知；无变化时安静，任务页提供随时查看的状态。

**退出条件**：AT18–AT20 通过；至少一次实际模型处理批次成功入库，一次受控中断后继续，一次重复运行不重复落库；任务状态与真实文件一致。确定性夹具可覆盖故障窗口，但不能代替实际语义转库和宿主后台证据。

**失败回退**：暂停剩余范围，保留已完成结果和悬项；修复后按输入/规则版本继续。若宿主只能在活跃任务中运行，明确这一限制并提供恢复入口；不为冒充无人值守而偷偷运行独立付费模型代理。

**证据与下一道门**：批次台账、输入/输出指纹、真实用量与通知、恢复记录和资料问题清单。驾驶员验收“可以离开去做别的事、回来有结果且能处理失败”的体验后进入 P6。
