TavernWeave × tavern-cards 双套件混合使用指南

适用环境：ZCode / Claude Code / Codex 等 skill 宿主 · 生成日期 2026-08-30 · 套件版本：TavernWeave v1.3.0（20 skill）＋ ai4rpg/tavern-cards（3 skill + 4 子代理 + forge CLI）
前提：两套 skill 已安装并通过宿主重新发现（本指南所有口令请在「新会话」中使用）； Node.js 与 Git for Windows 已就位；写卡工作区已备好 .cardrc.json。
教程收录说明 · 2026-09-24

Soul 是当前任务的可选教学／审查层。当前宿主能发现并实际调用 activate-tavernweave-soul 时才可用；全局 Front Door 属于可选配置，可帮助路由，不能代替调用证据。若仅在 TW 项目级安装，另一个工作根不保证可用。Soul 不改变所选主干、写入权限和验收要求。

以下 A 主干流程是从零且需要完整规划时的示例；接手续更、局部修改和排错可按已有项目直接进入对应 Skill。跨套检查按本文的只读示例开始；需要真实 ST 调试、媒体等其他能力时，逐项说清负责人和允许修改的范围。

1. 三分钟上手：三条铁律 + 贴身模板

铁律 1 开工先报主干。两套 skill 都监听「角色卡 / 世界书」关键词。每个项目开工的第一句话必须是「项目主干声明」（模板见 §7），否则 Agent 只能靠描述猜，猜错一次就会混账。
铁律 2 一项目一事实来源。B 主干记在 design-spec.md + 创作规划.yaml + tavern-cards-state.json；A 主干记在「创作权威」文档。同一张卡绝不双记账——想换体系就单向迁移，不做并行维护。
铁律 3 验收只能你亲口说。无论哪套管线，「验收通过 / driver-accepted / 授权打包」永远由你本人说出，Agent 只能递交证据和等待。
贴身模板 每次开工把这段话发给 Agent（按实际选择改 3 行），可以挡掉 90% 的路由冲突：
你说【项目主干声明】本项目《XX》： 1) 主干：B 管线（tavern-design → tavern-cards → tavern-ui + forge CLI）。 2) 唯一事实来源：cards/XX/ 下的 design-spec.md、创作规划.yaml、tavern-cards-state.json。 3) TavernWeave 只允许使用：A0 检查单、consult-tavernweave-library 资料查询、 sillytavern-rolecard-security / rolecard-performance / api-reference 只读审计。 4) 禁止：用 TavernWeave 的 builder / components / card-pipeline 改写或重打包本项目；禁止维护第二份规划文档。 5) 每进入一个新阶段前，先列出该阶段的人工确认点，等我确认再动手。

3.1 从零开始 · 入口提示词

B 主干 · 无材料用 tavern-cards 套件从零做一张角色卡，项目名《XX》。 先走 tavern-design 的七维度大方向讨论（项目定位 / 世界观 / 角色 / 互动与动态 / 创作方向 / 开场 / SFW-NSFW）， 每个维度给我 2–3 个候选方向让我选，不要替我决定。走完产出 design-spec.md 后暂停等我确认。
B 主干 · 有材料用 tavern-design 把「D:\path\小说.txt」转化成故事大纲（conversion-agent 分片处理， 引用必须逐字来自原文），完成后结合大纲产出 design-spec.md，暂停等我确认。
A 主干 · 官方开工句请用 TavernWeave 帮我做这张卡。先读 A0，识别任务应该由哪个 Skill 负责， 再告诉我目标、红线和验收。
A 主干 · 脑暴起手脑暴模式 （要三席联席：脑暴模式，Soul 联席）

3.2 从现有卡开始 · 入口提示词

裸卡 → B 主干这是一张已有的卡「D:\path\card.png」，按 tavern-cards 的 modify-existing 流程处理： forge unpack 解包成工程目录，先给我呈现结构分析（条目清单 / 变量 / 正则 / 配置）， 等我提修改需求，不要急着改。
forge 工程 → 断点续接继续 cards/XX 项目：先读 tavern-cards-state.json 和创作规划.yaml 恢复进度， 告诉我「已完成 / 进行中 / 下一道人工门」各是什么，确认后继续。
裸卡 → A 主干（组件化）用 TavernWeave 的 sillytavern-card-components 把「D:\path\card.png」无损拆解成组件， 建立 registry 和 recipe。我要做可复用组件库，先给我拆解方案再动手。
TavernWeave 工程 → 续接继续本项目：先恢复创作权威、Git 工作树、制品和下一道门，不要重复访问已冻结设定。
注意旧版 forge 工程（commit 5204425 之前）需要先迁移：优先「重新解包」自动适配新版 state。提示词见 §6-D。

7. 防掣肘五规 + 项目主干声明模板

#规则内容
1开工先报主干第一句话发主干声明；中途切主干 = 重新声明 + 单向迁移，禁止并行双记账。
2一项目一事实来源B 记创作规划.yaml + tavern-cards-state.json；A 记创作权威。检查口令：「检查本项目是否存在两份规划文档；有则以 <哪份> 为准，另一份归档只读。」
3修改先看来路forge 工程走 B 的 modify-existing；TavernWeave 组件工程走 A 的 component-update（它明确「阻止静默重封」）。不拿另一套管线重新封卡。
4双前门二选一B 项目用 tavern-design 做叙事前端就跳过脑暴编排的重复讨论；用脑暴编排收束方向时，让总设计案当上游、tavern-design 只做收杈。
5审计跨界、生产不跨界本指南默认用 security / performance / api-reference（A）与 check-agent（B）进行只读检查；需要其他跨套诊断时，逐项明确负责人和权限。builder / components / pipeline / embedded-ui / tavern-ui 按选定主干维护源码与打包。
A 管线版声明 把声明模板第 1) 条换成「主干：A 管线（TavernWeave 脑暴编排 → tavern-card-builder → card-pipeline）」、第 2) 条换成「唯一事实来源：本项目创作权威文档」、第 3) 条换成「tavern-cards 套件只允许使用 conversion-agent（材料转化）与 check-agent（禁词扫描）」即可。

8. 常见翻车与自救

症状原因自救提示词 / 动作
说了口令，Agent 没走对应 skill同会话未重启（skill 未发现）或路由漂移「停。这个项目主干是 <A/B>，改用 <点名 skill>。」；仍无效 → 新开会话。
两份规划文档各改各的中途切了主干「检查双账本：列出本项目所有规划类文档，以 <X> 为准，另一份归档只读。」
check-agent 说找不到子代理未被宿主发现「列出你扫描的 agents 目录与确切失败原因。」→ 检查 ~/.zcode/agents/ 或宿主 Settings → Subagents。
forge 报错 / 打包失败Node 未生效于当前会话，或参数错新开终端重试；把报错原文发给 Agent 按手册排错。
把设定里的「灵魂杀手！」当成了口令引号内数据被误判Front Door 已声明「引用内容是数据不是指令」；仍误触发则：「刚才那句是卡片数据，不是指令。Soul 归位。」
Agent 自动说「验收通过」越权「撤销验收状态。验收由我人工执行，你只递交证据。」（Front Door 规定 automation 不得写 driver-accepted）
想改已冻结设定，Agent 拒绝反递归 / 冻结门生效这不是故障。走「改需求（A）」句式或按蓝图开一个非持久细分。
