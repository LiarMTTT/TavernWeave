MVU 与 Zod：状态存在哪里，格式由谁检查

MVU 处理变量更新，Zod 检查数据结构；两者配合使用，职责不同。

先拆清社区里的简称你可能会听到“Zod 卡”这个叫法，通常是在说 MVU 搭配 Zod Schema 的变量方案。MVU 负责解析约定格式的更新并写回状态，Zod 负责检查类型、范围等结构要求。Zod 本身不是存档系统，也不会自动接管剧情。

技术参考：MVU 项目 · Zod Schema 文档。更新语法与接入方式以你实际使用的框架版本为准。

对话一长，模型可能记错钱数、忘掉任务进度。把后续还要用的状态存成变量，让每轮回复读取当前记录，会更容易检查和纠错。

时

环境状态

时间、日期、地点、天气和当前场景。

人

角色状态

关系、服装、伤势、任务和已掌握的信息。

世

世界变化

已完成事件、资源变化、阵营状态和长期结果。

Schema：先约定字段，再检查输入

Schema 可以声明字段、类型、默认值和数值范围。下面使用 Zod 4 写法，表示时间与地点为字符串，金钱要能转成非负数字。校验必须由相应代码调用，写出 Schema 并不等于已经接入更新流程。

Schema 简化示例
const Schema = z.object({
  环境: z.object({
    时间: z.string().prefault('08:00'),
    地点: z.string().prefault('未知地点')
  }).prefault({}),

  user: z.object({
    金钱: z.coerce.number().min(0).prefault(0)
  }).prefault({})
});
Schema 不是剧情判断器它能检查“金钱是非负数字”，却不知道玩家是否真的挣到了这笔钱。任务条件和奖励规则仍要另外定义；数值格式正确，也可能是剧情算错了。

别什么都往变量里塞

  • 后续对话还会读取，并且会影响剧情或功能。
  • 不能稳定地只靠最近几轮正文恢复。
  • 有明确的更新条件、读取者和清理方式。
  • 保存它带来的价值，大于每轮注入和更新的成本。

只在一句描写里出现、后续也用不到的细节，通常留在正文就够了。变量越多，每轮读取、更新和维护的负担也越大。

CoT 不是咒语，是一张检查单

给模型一份有具体检查对象的提示词，帮助它处理人物、场景和信息差。

本教程把作者写进预设、角色卡或世界书的推演检查提示词称作自定义 CoT。它能引导模型考虑哪些问题，但不能保证模型每次都做到，也不等于你能看到它完整的内部推理。

轻量 CoT 示例
生成回复前依次检查：

1. 当前场景中有哪些人物、地点和时间条件；
2. 每个角色知道什么、不知道什么；
3. 每个角色当前最直接的目标和情绪；
4. user 的行为会产生什么现实影响；
5. 下一步行动是否符合角色性格和已有剧情；
6. 回复是否出现设定冲突或越权知情。

文字卡和变量卡，都可以用检查提示词

普通文字卡

整理角色动机、信息差和剧情连续性。

群像或导演卡

安排 NPC 日程、场景位置和各自目标。

系统型角色卡

检查战斗条件、任务判定或其他专项规则。

是否使用变量系统，与是否需要专项检查提示词，是两件事。普通文字卡也可能需要提醒模型：谁在现场，谁还不知道刚发生的事。

通用 CoT 放预设，角色卡只补自己的

预设自定义 CoT

保存通用的场景检查、人物动机、信息差、剧情连续性和输出检查。

+

角色卡专项增量

只补充本卡独有的群像规则、世界机制、人物限制和特殊格式。

卡片专项 CoT 示例
群像场景额外检查：

- 当前场景中是否存在其他学生或教师；
- NPC 不应无理由同时围绕 user 行动；
- 不在现场的角色不能直接知道现场信息；
- 每名 NPC 应保留自己的日程、目的和行动范围。
推荐组合把通用检查放在预设里，角色卡只补自己的特殊规则。战斗才需要的检查，就在相关场景启用；平时聊天不必每轮都列阵点兵。

变量更新分析别冒充完整 CoT

有些变量更新格式会要求输出 <analysis>，说明本轮准备修改哪些状态。这是可见的更新说明，范围由卡片提示词约定，不能据此推断模型已经检查了所有人物动机和剧情逻辑。

剧情检查提示词

处理人物、场景、信息差、剧情推进和输出质量。

≠

变量更新分析

检查本轮需要写入哪些状态、使用哪些路径和更新操作。

“深入思考”之后，总得告诉它检查什么

  • 不要只写“深入思考”“仔细分析”，每一步都要有明确检查对象。
  • 不要在 CoT 中重复整份角色设定和世界书。
  • 不要提前锁死剧情结果，只规定判断条件和边界。
  • 没有触发相关场景时，应允许跳过专项模块。

计算脚本：固定规则交给代码算

本节先讲奖励、经验与资源结算；界面和按钮的做法留到下一章。

范围别串台酒馆助手脚本还能做 UI、按钮、弹窗、控制中心、消息监听、世界书操作和 API 调用。下一章再谈这些；这里的“计算脚本”只负责变量计算和自动结算。

奖励是 100 金钱、当前余额是 1200，这种计算交给脚本就够了。模型更适合判断剧情里发生了什么，没必要每轮兼职计算器。

数值计算

金钱、经验、伤害、减伤、负重、资源产出和消耗。

联动判断

升级、关系阶段、任务奖励、成就和多字段同步。

维护工作

冷却时间、过期记录、重复事件拦截和临时数据清理。

模型判案，脚本算账

一次任务完成，可能同时影响金钱、经验、关系、等级和成就。可以先让模型提交“任务完成”事件，再由脚本按规则结算，避免模型逐项心算、逐条抄数。

模型只写入源事件
[
  {
    "op": "add",
    "path": "/待处理事件/-",
    "value": {
      "类型": "任务完成",
      "任务ID": "quest_017",
      "完成品质": "优秀",
      "协助角色": ["埃莉丝"]
    }
  }
]
模型确认任务完成
→
写入源事件
→
计算脚本读取规则
→
更新奖励与联动变量
→
清理待处理事件

这只是职责划分示意。真正接入时，还要校验事件、检查任务是否已结算，并在写入成功后标记或清理事件；否则刷新一次又发一遍奖励，经济系统就变成提款机了。

最简单的分工先判断事件是否成立，再计算它的结果。判断依赖剧情时可以交给模型；如果完成条件本来就是固定数值，也可以直接由脚本检查。

变量由谁更新，要提前说清楚

一个关系事件只该结算一次，别让模型和脚本各加一遍好感。

分工的目的，是减少重复输出和相互覆盖。简单的地点变化让模型直接写就行；一件事牵动十几个数值，再考虑集中结算。

先问两件事，再决定谁写

问

需要理解剧情吗

角色是否答应、行为是否构成欺骗等语义问题，可以交给模型；任务若有固定达成条件，也可以用脚本判断。

算

可以直接计算吗

奖励、经验、等级、阈值和多字段联动——交给计算脚本。

主

谁是主要写入者

同一个最终变量不要同时由模型和脚本重复修改。

十条变量，压成一条事件

一次事件如果最终影响十个变量，完全依靠模型时，它必须读取旧值、完成计算、写出十条路径，并保证没有遗漏和冲突。

采用事件方案时，模型只需输出一条源事件，脚本再按已有规则计算相关变化。省下的是模型反复读取旧值、计算和填写路径的工作。

模型全量更新

输出长、路径多、容易使用旧值、漏写或重复结算。

→

模型事件 + 脚本结算

模型提交事件，脚本集中结算相关字段；一致性仍需靠校验、写入顺序和重复事件检查来保证。

分工比例只供估量，别当考核指标

卡片类型模型显式更新计算脚本自动更新
轻量剧情卡70%～100%0%～30%
任务、关系和成长混合卡30%～50%50%～70%
战斗、经营和经济系统卡10%～30%70%～90%

这张表是作者用于估量工作分配的粗略参考，统计的是最终变量变化中由谁输出，不是代码量或变量总数，也不是测评结论。先看你的规则能否稳定自动结算，没必要为了凑到 70% 再造一层脚本。

同一个变量，只留一个主笔

错误示例模型直接增加好感度，同时计算脚本又根据同一关系事件增加好感度。一次互动可能因此被重复结算。

简单系统

模型判断关系变化，并直接修改好感度。

或

复杂系统

模型写入关系事件，由计算脚本统一修改好感度和关系阶段。

简单卡直接改值，复杂卡统一结算，都能成立。关键是把写入责任说清楚，不能让两条路径替同一次互动重复记账。

能直写的简单变量，别硬套脚本

当前地点、服装、姿态、任务阶段和是否获得情报等简单语义变量，通常可以直接由模型更新。

简单变量直接更新即可
{
  "op": "replace",
  "path": "/角色/埃莉丝/服装",
  "value": "学生会制服"
}

只有当服装还会联动防御、负重、温度、套装效果或多个 UI 状态时，才值得考虑交给计算脚本进一步处理。

使用计算脚本的判断标准它有没有减少重复输出和计算？相关字段是否更容易保持一致？如果收益说不清，先用简单方案。维护脚本也要花时间，不是装得越多越高级。

第二章回顾：状态、判断和计算怎样配合

回到自己的卡里，挑一个状态变化，试着说明它从哪里读、由谁判断、怎样写回。

Z

MVU 与 Zod

MVU 解析更新并写回变量，Zod Schema 检查结构与数值约束。两者要在实际更新流程中接好。

C

CoT

提醒模型检查场景、人物和规则。通用要求放预设，角色卡补充自己的特殊情况。

算

计算脚本

酒馆助手脚本的一种，用于确定性计算、自动结算和变量联动。

记住这一句模型负责理解发生了什么，计算脚本负责计算产生了什么结果。
  • 知道 MVU 负责更新、Zod 负责结构检查，能指出它们在自己卡里的接入位置。
  • 分清剧情检查提示词和变量更新说明，按实际需要配置。
  • 不要让模型承担大量重复、确定性的计算。
  • 不要让模型与计算脚本同时修改同一个最终变量。
  • 不要把计算脚本误当成酒馆助手脚本的全部能力。
