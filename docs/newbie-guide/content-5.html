Zod：别把长期状态寄存在模型脑子里

这里的 Zod，指社区常说的 MVU Zod 整套方案。

叫法先统一底层更新机制来自 MVU，结构约束使用 Zod Schema；角色卡圈通常把这套组合直接叫“Zod”。后文也这么叫，免得把一套东西讲成两门课。

时间、金钱、关系、任务这些长期状态，别指望模型靠长对话硬记；交给 Zod 留账。

时

环境状态

时间、日期、地点、天气和当前场景。

人

角色状态

关系、服装、伤势、任务和已掌握的信息。

世

世界变化

已完成事件、资源变化、阵营状态和长期结果。

→

变量账本长什么样

简化后的变量示例
环境:
  日期: 2026-07-26
  时间: 14:30
  地点: 学生会办公室

user:
  金钱: 1200
  当前任务: 调查旧校舍

角色:
  埃莉丝:
    好感度: 42
    当前状态: 工作中

模型不需要每轮重新生成整棵变量，只需要更新真正发生变化的路径。

一次简单的变量更新
[
  {
    "op": "replace",
    "path": "/环境/时间",
    "value": "15:10"
  },
  {
    "op": "replace",
    "path": "/角色/埃莉丝/当前状态",
    "value": "前往旧校舍"
  }
]

Schema 是变量的户口本

Schema 用来规定变量有哪些字段、是什么类型、缺少时使用什么默认值，以及数值允许落在什么范围。

Schema 简化示例
const Schema = z.object({
  环境: z.object({
    时间: z.string().prefault('08:00'),
    地点: z.string().prefault('未知地点')
  }).prefault({}),

  user: z.object({
    金钱: z.coerce.number().min(0).prefault(0)
  }).prefault({})
});
Schema 不是剧情判断器它能规定“金钱必须是非负数字”，但不会自动理解任务是否完成，也不会自动决定完成任务应该奖励多少钱。

别什么都往变量里塞

  • 后续对话还会读取，并且会影响剧情或功能。
  • 不能稳定地只靠最近几轮正文恢复。
  • 有明确的更新条件、读取者和清理方式。
  • 保存它带来的价值，大于每轮注入和更新的成本。

只在一句描写中出现、以后不会再使用的信息，没有必要全部塞进 Zod。

CoT 不是咒语，是一张检查单

它不依赖 Zod；硬把两者绑死，只会多造一个误区。

这里的 CoT，指作者写进预设、角色卡或世界书里的自定义推演步骤。

轻量 CoT 示例
生成回复前依次检查：

1. 当前场景中有哪些人物、地点和时间条件；
2. 每个角色知道什么、不知道什么；
3. 每个角色当前最直接的目标和情绪；
4. user 的行为会产生什么现实影响；
5. 下一步行动是否符合角色性格和已有剧情；
6. 回复是否出现设定冲突或越权知情。

没装 Zod，照样能用 CoT

普通文字卡

整理角色动机、信息差和剧情连续性。

群像或导演卡

安排 NPC 日程、场景位置和各自目标。

系统型角色卡

检查战斗条件、任务判定或其他专项规则。

Zod 卡可以没有专项 CoT；没有任何变量的文字卡，也可以使用复杂 CoT。

通用 CoT 放预设，角色卡只补自己的

预设自定义 CoT

保存通用的场景检查、人物动机、信息差、剧情连续性和输出检查。

+

角色卡专项增量

只补充本卡独有的群像规则、世界机制、人物限制和特殊格式。

卡片专项 CoT 示例
群像场景额外检查：

- 当前场景中是否存在其他学生或教师；
- NPC 不应无理由同时围绕 user 行动；
- 不在现场的角色不能直接知道现场信息；
- 每名 NPC 应保留自己的日程、目的和行动范围。
推荐组合预设通用 CoT + 角色卡专项增量 + 按条件触发的特殊模块。不要让每张卡重复携带一整套相同 CoT。

变量更新分析别冒充完整 CoT

Zod 更新格式中可能包含一段 <analysis>，它只负责判断哪些变量需要更新、路径是什么，以及应该新增还是替换。

完整 CoT

处理人物、场景、信息差、剧情推进和输出质量。

≠

变量更新分析

只检查本轮有哪些状态需要写入 Zod。

空话 CoT 不如不写

  • 不要只写“深入思考”“仔细分析”，每一步都要有明确检查对象。
  • 不要在 CoT 中重复整份角色设定和世界书。
  • 不要提前锁死剧情结果，只规定判断条件和边界。
  • 没有触发相关场景时，应允许跳过专项模块。

计算脚本：把重复算术从模型手里抢回来

这里只算变量和自动结算；按钮、弹窗和 UI 留到下一章。

范围别串台酒馆助手脚本还能做 UI、按钮、弹窗、控制中心、消息监听、世界书操作和 API 调用。下一章再谈这些；这里的“计算脚本”只负责变量计算和自动结算。

输入已经明确、按固定规则总能得到同一结果的活，就别浪费模型脑力，让脚本接管。

数值计算

金钱、经验、伤害、减伤、负重、资源产出和消耗。

联动判断

升级、关系阶段、任务奖励、成就和多字段同步。

维护工作

冷却时间、过期记录、重复事件拦截和临时数据清理。

模型判案，脚本算账

例如一次任务完成后，需要增加金钱、经验、关系值，并检查升级和成就。模型没有必要把所有结果逐条算完。

模型只写入源事件
[
  {
    "op": "add",
    "path": "/待处理事件/-",
    "value": {
      "类型": "任务完成",
      "任务ID": "quest_017",
      "完成品质": "优秀",
      "协助角色": ["埃莉丝"]
    }
  }
]
模型确认任务完成
→
写入源事件
→
计算脚本读取规则
→
更新奖励与联动变量
→
清理待处理事件

模型只需要理解“发生了什么”；计算脚本再处理这件事会产生哪些确定结果。

最简单的分工需要理解剧情含义的判断交给模型；根据已有输入可以直接算出的结果交给计算脚本。
14

模型判案，脚本算账：别抢同一支笔

这里分的是工作，不是给游戏数值找“五五开”。

目标不是凑比例，而是尽量少让模型每轮亲手输出一长串变量。

先问两件事，再决定谁写

问

需要理解剧情吗

任务是否完成、角色是否答应、行为是否构成欺骗——交给模型。

算

可以直接计算吗

奖励、经验、等级、阈值和多字段联动——交给计算脚本。

主

谁是主要写入者

同一个最终变量不要同时由模型和脚本重复修改。

十条变量，压成一条事件

一次事件如果最终影响十个变量，完全依靠模型时，它必须读取旧值、完成计算、写出十条路径，并保证没有遗漏和冲突。

计算脚本可以把十几条结果压缩成一条源事件，再从这条事件自动推导其余变化。

模型全量更新

输出长、路径多、容易使用旧值、漏写或重复结算。

→

模型事件 + 脚本结算

模型只做语义判断，脚本统一计算并保持多字段一致。

比例怎么抓：给你一把粗尺

卡片类型模型显式更新计算脚本自动更新
轻量剧情卡70%～100%0%～30%
任务、关系和成长混合卡30%～50%50%～70%
战斗、经营和经济系统卡10%～30%70%～90%

这里统计的是最终变量变化中，需要模型亲自输出的比例，不是代码量，也不是变量总数。这只是经验参考，不是必须达到的指标。

同一个变量，只留一个主笔

错误示例模型直接增加好感度，同时计算脚本又根据同一关系事件增加好感度。一次互动可能因此被重复结算。

简单系统

模型判断关系变化，并直接修改好感度。

或

复杂系统

模型写入关系事件，由计算脚本统一修改好感度和关系阶段。

两种方案都可以。关键是同一个最终结果只保留一个主要写入者。

能直写的简单变量，别硬套脚本

当前地点、服装、姿态、任务阶段和是否获得情报等简单语义变量，通常可以直接由模型更新。

简单变量直接更新即可
{
  "op": "replace",
  "path": "/角色/埃莉丝/服装",
  "value": "学生会制服"
}

只有当服装还会联动防御、负重、温度、套装效果或多个 UI 状态时，才值得考虑交给计算脚本进一步处理。

使用计算脚本的判断标准它是否能明显减少模型输出、避免重复计算，或保证多个变量始终一致。如果不能，就不要平白增加工程复杂度。

第二章收口：谁记账，谁推演，谁算数

三个岗位分清，模型少背债，变量也少打架。

Z

Zod

保存和更新长期状态。本文中的 Zod 已包含 MVU 变量更新机制。

C

CoT

独立的推演提示词。通常以预设通用 CoT 加角色卡专项增量的方式使用。

算

计算脚本

酒馆助手脚本的一种，用于确定性计算、自动结算和变量联动。

记住这一句模型负责理解发生了什么，计算脚本负责计算产生了什么结果。
  • 不要把 MVU 和 Zod 拆成两套并列的新手课程。
  • 不要把 CoT 与 Zod 强绑定，也不要把变量更新分析当成完整 CoT。
  • 不要让模型承担大量重复、确定性的计算。
  • 不要让模型与计算脚本同时修改同一个最终变量。
  • 不要把计算脚本误当成酒馆助手脚本的全部能力。

下一章将继续介绍酒馆助手脚本的其他能力，以及正则如何参与 UI、显示和交互流程。
