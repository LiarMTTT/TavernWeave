用一段状态文本认识正则

先约定标签，再决定匹配后是隐藏、提取还是替换。

假设模型总是按下面的格式输出地点和时间，就可以利用标签定位这一段。格式越稳定，匹配规则越容易写，也越容易测试。

结构化输出示例
<status>
地点：学生会办公室
时间：14:30
</status>

正则可以识别 <status>...</status>，将内容隐藏、提取，或替换成固定的展示结构。

适合正则

固定标签、简单字段、前后缀、格式清理和展示替换。

VS

不适合正则

复杂状态、异步请求、多步骤交互、持久化和生命周期管理。

越修越长时，回头看看输入格式同一条正则不断增加分支，往往说明输入已经不稳定，或任务超过了简单文本匹配的范围。先考虑统一格式，复杂结构再交给解析器或脚本处理。

隐藏更新块时，保留变量系统需要的原文

玩家可以只看剧情，变量系统仍要读到完整的更新指令。

采用约定更新格式的变量卡，可能要求模型输出这样的标签块：

变量更新块
<UpdateVariable>
  ...
</UpdateVariable>

这部分供变量系统解析，未必需要展示给玩家。可以通过显示层的正则规则隐藏，但原始消息与解析输入必须按更新框架的要求保留。

模型输出正文与更新块
→
变量系统取得完整更新块
→
正则处理显示
→
用户只看到正文
这张图说明依赖关系变量系统必须取得完整的解析输入；它与显示正则实际怎样执行，要按当前宿主和扩展配置核对。不要把“隐藏给玩家看”做成“在解析前删除原文”，否则页面干净了，变量也不更新了。

把选项标签变成可点击按钮

先生成按钮，再接上点击时要执行的动作。

例如模型输出：

模型输出标签
<choice>前往旧校舍</choice>

正则可以替换成：

替换后的静态外观
<button>前往旧校舍</button>

这个示例只创建按钮元素。要让点击产生效果，还需要脚本或宿主提供事件处理；使用酒馆助手脚本时，可以按下面的流程连接：

正则生成按钮外观
→
脚本找到新元素
→
绑定点击事件
→
发送消息或修改数据
→
反馈结果
先约定这个按钮到底做什么点击后发送“前往旧校舍”，和直接修改地点变量，是两种不同设计。先确认玩法，再绑定相应行为，别让界面暗中替剧情做决定。
29

固定界面模板，让模型只填内容

任务标题和进度可以变，页面结构、样式与交互入口尽量保持稳定。

让模型直接输出任意 HTML，常见问题包括：

  • 标签没有闭合，导致后续楼层布局被破坏。
  • class、字段和层级每轮变化，脚本无法稳定识别。
  • 内联样式污染主题和移动端显示。
  • 输出变长，挤占正文和变量更新空间。
  • 出现不安全或无法预测的页面内容。

如果界面只需要标题、状态和进度，可以让模型按约定输出这些字段，再检查数据是否符合要求：

结构化数据示例
{
  "标题": "调查旧校舍",
  "状态": "进行中",
  "进度": 60
}
模型输出有限字段
→
解析并校验数据
→
使用固定模板渲染
→
展示内容并连接交互
内容变，模板不用跟着重写固定 DOM、class 与按钮入口，可以减少每轮布局变化。JSON 交给 JSON 解析器处理，展示前按需要转义文本；不要把模型返回的任意内容直接当 HTML 执行。

选正则还是脚本，先看要完成什么

只处理文本，可以先用正则；涉及状态、事件和请求，就需要程序逻辑。

正

只处理文本

匹配、隐藏、提取、清理和简单替换，优先正则。

脚

需要逻辑或状态

判断、变量、保存、请求、监听和交互，使用脚本。

合

文本变成交互

正则生成结构，脚本绑定行为，两者配合。

工具选择口诀
找出来、藏起来、换个样子
→ 正则

点了以后做事、数据变化后刷新、失败后反馈
→ 酒馆助手脚本

模型输出要变成可交互界面
→ 正则 + 脚本
上面的口诀只是入门判断结构化数据也可以由脚本直接解析，并非所有模型输出都必须经过正则。选择时看输入格式和目标行为，别为了少写两行，把维护成本留到后面。

常见故障：从现象开始找线索

下表列的是常见原因，先用源码和运行结果核对，再决定改哪里。

现象常见原因
页面看得到，但按钮不能用只生成了 HTML，没有绑定脚本事件。
按钮第一次有效，刷新后失效只在首次加载时绑定，没有处理重新渲染。
点击一次执行多次监听器重复注册，或没有执行锁。
状态栏一直显示旧数据只初始化读取一次，没有监听变量变化。
正则把正文也隐藏了匹配范围过大或边界不明确。
变量更新突然失效正则破坏了更新块，或执行顺序不正确。
UI 变了，刷新后恢复只改了 DOM，没有写入真实状态。
变量已变化，UI 没变化写入成功，但没有重新读取和渲染。
把实际情况告诉 Agent“切换聊天后第一次点击没反应，再点一次就好了”，已经有可追查的线索。再附操作步骤、预期结果和相关报错，排查会容易得多。

确认项目以哪份数据为准，再检查界面有没有正确反映它。

真实状态

保存在变量、设置、消息或其他明确持久层中的数据。

→

页面当前显示的文字、卡片、进度条和选中效果。

脚本验收：到真实酒馆里走一遍

离线环境帮助检查布局和部分逻辑；宿主 API、聊天数据与生命周期还要在真实环境确认。

按功能选择需要验收的路径

让 Agent 先说明已检查的内容，再列出需要你操作的面和点。下列路径适用的都要覆盖；项目没用到的能力，注明不适用及原因。

  • 新建对话时能否正常初始化。
  • 刷新页面后是否仍然有效。
  • 切换对话和消息楼层后是否读取正确数据。
  • 按钮是否只执行一次，并能处理快速连点。
  • 重复打开面板是否产生重复 DOM 或监听器。
  • 变量和设置是否真正写入。
  • UI 是否跟随真实数据刷新。
  • 正则是否只匹配目标内容。
  • 脚本禁用或重载后是否存在残留。
  • 控制台是否出现新的错误。
  • 移动端是否可读、可点、无横向溢出。
  • 外部资源失败时是否有明确提示和降级。

离线检查之后，还有哪些要去酒馆确认

不能证明 API 可用

离线替身可以检查调用约定；真实宿主是否提供该函数、事件是否触发，还要接入确认。

不能证明持久化成功

演示页里的状态变化不能证明真实聊天或消息变量已保存，需要写入后重新读取。

不能证明生命周期正确

真实环境里的刷新、聊天切换、脚本重载和生成事件，需要分别走过对应路径。
