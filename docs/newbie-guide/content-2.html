03

模型、开发 Agent 和副驾驶，怎样分工

先看你缺的是文笔、工程能力还是并行处理时间，再决定要不要增加工具。

成人内容边界本节讨论合法、虚构、角色明确成年且基于自愿关系的成人向创作。未成年人性内容、年龄不明确的性内容、现实人物私密色情内容及其他违法剥削内容不属于正常创作范围。

先认清这三个岗位

文

内容模型

帮助你写人物、世界观、剧情和对白；能否处理指定题材，要结合模型表现与服务规则判断。

工

开发 Agent

负责项目文件、代码、变量系统、前端、构建、调试和 Git。

副

副驾驶 Agent

同时处理另一项工程任务。可以共享资料，但写入目录要隔离，避免两边互相覆盖。

岗位不必由同一个模型承担某个模型代码能力强，不代表它适合写角色关系；某个模型成人内容限制较少，也不代表它适合维护工程文件。

第三方模型接入：先测工具链，别只测聊天

这里接 API，不买 ChatGPT 套餐下面讲的是怎样让 Codex 使用 DeepSeek、Kimi、GLM、MiniMax 或其他兼容 API；套餐购买在上一节，别把两笔账搅在一起。

接通后能回复“你好”，只说明最短的一次请求通了。要拿它处理项目，还得检查下面这些能力：

  • 是否支持 Responses API，或是否能从 Chat Completions 正确转换。
  • 是否能处理工具调用、流式输出和长任务中的连续状态。
  • 模型 ID、上下文窗口和自动压缩阈值是否准确。
  • 图片、插件、MCP、Skill 等能力是否完整兼容。
  • 供应商如何计费，以及怎样存储提示词、源码和上传文件。

CC Switch：同时管理多个 Agent 工具

CC Switch 适合同时使用 Codex、Claude Code、Gemini CLI 等工具，并且需要频繁切换多个供应商的用户。

  1. 从 CC Switch 官方仓库或官方 Releases 下载最新版。
  2. 打开 Codex 页面，点击右上角的 +。
  3. 优先选择内置供应商预设。
  4. 填写自己的 API Key，检查 Base URL、模型 ID 和模型映射。
  5. 保存并启用供应商，然后完全退出并重启 Codex。
  6. 执行一个只读测试任务，并在供应商控制台确认实际请求。
什么时候需要本地路由原生支持 Responses API 的供应商通常可以直接连接。只支持 Chat Completions，或者使用非默认模型名的供应商，需要开启“需要本地路由映射”，并保持 CC Switch 本地路由与 Codex 接管运行。修改模型映射后也应重启 Codex，因为模型目录通常在启动时加载。

Codex++：专注管理 Codex 桌面端

Codex++ 更适合主要使用 Codex 桌面端，希望集中管理供应商、模型目录、会话和诊断功能的用户。

  1. 从 Codex++ 官方 Releases下载对应系统的版本。
  2. 先打开“Codex++ 管理工具”，检查官方 Codex 应用路径和运行状态。
  3. 新建供应商并选择“纯 API”模式。
  4. 填写协议、Base URL、API Key、模型 ID 和上下文窗口。
  5. 运行模型测试或 Provider Doctor。
  6. 保存后从 Codex++ 入口启动应用，再用只读项目验证模型、工具调用和流式响应。
桌面端兼容性会变化Codex++ 通过外部启动器、本地辅助服务和界面增强与官方桌面应用配合，不修改官方应用的 app.asar。但它仍依赖官方应用的页面结构和本地数据格式；官方应用升级后，部分增强功能可能需要等待适配。

国内环境付费避雷：先验交付，再买额度

作者的使用意见基于作者此前在国内环境的实际体验，不推荐购买 Cursor Pro+ 或 Ultra；Kiro 中的 Claude 也没有通过作者对主力开发 Agent 的要求。下文保留这份判断和吐槽，供你选购时参考。本轮只重新核对公开机制，没有重新测试作者的账号，也不能替你判断当前账号的可用性。

Cursor：Fable／Opus 用不了，再大的套餐也只是大号空桶

作者购买高价套餐，看重的是在 Agent 里使用 Fable、Opus 等模型，而不只是编辑器顺手。在此前的国内使用环境中，这条工作流程没有正常跑起来，后面的付费判断也建立在这个前提上。

  • 当时的 Fable 没有形成可用的开发流程。
  • Opus 也没能稳定承担作者的正式项目。
  • 其余体验不足以让作者接受 Pro+ 与 Ultra 的价格。
  • 核心模型用不了，买更多额度也解决不了这个问题。

2026-09-04 核对时，Cursor 套餐页仍列出 Pro+ 为 Pro 的三倍 Agent 限额、Ultra 为二十倍。数字看着很诱人，但先问自己：我需要的模型能不能稳定完成工作？水龙头不出水，买个大号桶也没用。

别把 IDE 和套餐绑在一起买Cursor 的编辑、跳转和调试可以继续按需使用，但“Cursor 这个 IDE 顺手”不等于“Cursor Pro+／Ultra 值得续费”。国内环境没有先验完 Fable／Opus，就不要直接冲高价套餐。

想自己选供应商，可以看看 OpenCode

OpenCode 文档列出七十多种供应商，并支持自定义供应商、Base URL 和本地模型。作者更看重这种可替换性：先选当前环境里能用的上游，出现问题时可以换。换上游仍要重新核对工具兼容性和实际费用。

OpenCode 不是绕区神器它不会替你绕过模型供应商的地区规则，也不该拿来盗用订阅或共享账号。它的优势是选择更透明、替换更容易：用合法可用的 API 或官方支持接入，先跑真实任务，再决定给谁付钱。

Kiro：下拉框写着 Claude，不等于办事时真有 Claude 那股脑子

作者此前测试 Kiro 中的 Claude 时，遇到的是复杂要求理解不稳、连续执行不可靠，无法放心交付正式工程。这个评价针对当时的实际体验。下拉框可以写得很豪华，但你付钱要的是把活做完，不能只收一块招牌。

作者为什么不推荐直接付费当时的理解与执行表现没有达到主力 Agent 的要求。可以先用可用的试用额度跑自己的任务；仅凭 Claude、Sonnet 或 Opus 的名字，作者不会建议你购买套餐或直接交出正式项目。

Kiro Auto：任务由平台分配给模型

截至 2026-09-04，Kiro 官方文档仍说明 Auto 会按任务选择模型，其模型目录也列出不同能力与费用倍率的选项。因此选择 Auto 时，应按自动路由服务来评估，不能把它理解为始终固定使用自己心里那一个模型。

平台希望平衡质量、速度与成本，付费用户则要看这套分配是否适合自己的任务。简单补全和长时间多文件修改，对稳定性的要求不同，别用一次补全成功替整套工程体验打包票。

证据边界也要讲清楚官方资料能确认 Auto 会自动选择模型。至于手动指定 Claude 后是否被替换，仅凭一次答得不好无法证明。作者的使用评价可以很直接，但涉及后台机制，仍要拿得出对应证据。

开工前模型体检：雷达之后还要自己跑

给自己留三类固定测试：一个小修改、一组需要连着读的文件、一项需要调用工具并处理失败的任务。以后换模型或供应商时，用同一组任务比较，才知道变化发生在哪里。

给返工也记一笔账便宜的调用如果需要你来回纠正，未必省钱。除了账单，还要记下你花了多少时间解释、检查和收拾残局。

成人向创作，也要按内容需求选模型

NSFW 不等于违法、有害或没有创作价值。角色卡和互动叙事中的成人向内容，可能用于成年人之间的亲密关系、情色文学、成人角色扮演、服装与身体审美设计，以及完整的角色档案。

作者在选择内容模型时，会特别留意以下情况。即使角色明确成年、情节虚构且关系自愿，不同模型和服务也可能对任务作出不同处理：

  • 直接拒绝继续，导致剧情或角色卡开发中断。
  • 自动淡化关键内容，破坏角色状态和关系推进。
  • 把创作任务改写成说教或价值判断。
  • 擅自改变用户指定的题材、文风或人物行为。
  • 因为题材标签误伤正常的人设、身体和服装设计。
选择标准不要只问“哪个模型最聪明”，还要问：它能否在合法边界内稳定完成创作者真正提出的成人向任务。

Grok 提供补写和第二版本

在作者的方案中，Grok 主要尝试这些补充工作；是否采用，仍由创作者看过文本后决定：

  • 更直接的成人向场景和成人对话样本。
  • 身体、动作和互动细节的连续描写。
  • Claude 已经完成结构，但没有完成的正文。
  • 为同一场景提供另一种表达或强度版本。
  • 检查原始需求是否在改写过程中被过度淡化。

双 Agent 不是两个人抢方向盘

本教程中的副驾驶不是只负责审查的聊天模型，而是：

双开 Agent，共享总工作区例如同时运行 Codex 桌面端和 Claude Code Desktop；两者都能读取共享资料，但分别处理不同项目或完全隔离的写入目录。

这里的“副驾驶”指第二个执行 Agent，驾驶员仍然是你。双开的收益是同时处理不同任务；若两边争着改同一份文件，你省下的时间多半会花在合并冲突上。

双 Agent 的分工示例

组合主 Agent 任务副驾驶 Agent 任务
Codex + Claude CodeCodex 处理大型角色卡工程、TW Skill、模块化、多文件修改和项目治理。Claude Code 处理另一个独立的前端、预览、浏览器测试或调试项目。
Claude Code + CodexClaude Code 处理当前需要频繁运行和预览的前端项目。Codex 处理另一张角色卡、世界书、组件拆分或独立审计任务。
共享知识底座两边读取相同的 TavernWeave、ST 开发指南 DB、模板和命名规范，减少工程范式漂移。

双 Agent 的五条铁律

  • 不能同时修改同一个项目。即使表面上是不同文件，也可能同时触碰 Git 状态、构建产物、锁文件、配置、版本号和自动格式化结果。
  • 共享资料默认只读。00-Shared/ 中的 Skill、DB 和模板只有在专门维护任务中才允许修改。
  • 每个 Agent 必须声明写入范围。允许读哪里、允许写哪里、禁止碰哪里，都应在开工时明确。
  • 同项目更换执行 Agent 前先停止写入。完成检查，按已有授权保存 Git 版本并生成交接，再让接手的 Agent 重新读取项目。
  • 本教程的入门方案：同一项目只留一个写入 Agent。第二个可以只读分析，不能顺手改文件。进一步使用隔离 worktree 并行开发时，还需要明确合并负责人和共享资源边界。
错误示例Codex 和 Claude Code 同时打开 Projects/星月学院/ 并各自修改。两个 Agent 都可能基于过期文件继续工作，最终互相覆盖、撤销或污染 Git Diff。
