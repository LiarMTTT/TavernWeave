03

别把写手、工程师和副驾驶塞进一个模型

内容创作、工程开发、模型供应商、并行 Agent，各是各的岗位；人多不等于不翻车。

成人内容边界本节讨论合法、虚构、角色明确成年且基于自愿关系的成人向创作。未成年人性内容、年龄不明确的性内容、现实人物私密色情内容及其他违法剥削内容不属于正常创作范围。

开工前，先把三张工牌发对

文

内容模型

负责角色设定、世界观、剧情、对话样本、关系推进和成人向正文。

工

开发 Agent

负责项目文件、代码、变量系统、前端、构建、调试和 Git。

副

副驾驶 Agent

与主 Agent 双开，共享总工作区，但处理另一个独立项目或完全隔离的写入范围。

岗位不必由同一个模型承担某个模型代码能力强，不代表它适合写角色关系；某个模型成人内容限制较少，也不代表它适合维护工程文件。

第三方模型接入：先测工具链，别只测聊天

这里接 API，不买 ChatGPT 套餐下面讲的是怎样让 Codex 使用 DeepSeek、Kimi、GLM、MiniMax 或其他兼容 API；套餐购买在上一节，别把两笔账搅在一起。

能回一句“你好”，离能当开发 Agent 还远。接第三方供应商前，把下面几项逐个验掉：

  • 是否支持 Responses API，或是否能从 Chat Completions 正确转换。
  • 是否能处理工具调用、流式输出和长任务中的连续状态。
  • 模型 ID、上下文窗口和自动压缩阈值是否准确。
  • 图片、插件、MCP、Skill 等能力是否完整兼容。
  • 供应商如何计费，以及怎样存储提示词、源码和上传文件。

CC Switch：同时管理多个 Agent 工具

CC Switch 适合同时使用 Codex、Claude Code、Gemini CLI 等工具，并且需要频繁切换多个供应商的用户。

  1. 从 CC Switch 官方仓库或官方 Releases 下载最新版。
  2. 打开 Codex 页面，点击右上角的 +。
  3. 优先选择内置供应商预设。
  4. 填写自己的 API Key，检查 Base URL、模型 ID 和模型映射。
  5. 保存并启用供应商，然后完全退出并重启 Codex。
  6. 执行一个只读测试任务，并在供应商控制台确认实际请求。
什么时候需要本地路由原生支持 Responses API 的供应商通常可以直接连接。只支持 Chat Completions，或者使用非默认模型名的供应商，需要开启“需要本地路由映射”，并保持 CC Switch 本地路由与 Codex 接管运行。修改模型映射后也应重启 Codex，因为模型目录通常在启动时加载。

Codex++：专注管理 Codex 桌面端

Codex++ 更适合主要使用 Codex 桌面端，希望集中管理供应商、模型目录、会话和诊断功能的用户。

  1. 从 Codex++ 官方 Releases下载对应系统的版本。
  2. 先打开“Codex++ 管理工具”，检查官方 Codex 应用路径和运行状态。
  3. 新建供应商并选择“纯 API”模式。
  4. 填写协议、Base URL、API Key、模型 ID 和上下文窗口。
  5. 运行模型测试或 Provider Doctor。
  6. 保存后从 Codex++ 入口启动应用，再用只读项目验证模型、工具调用和流式响应。
桌面端兼容性会变化Codex++ 通过外部启动器、本地辅助服务和界面增强与官方桌面应用配合，不修改官方应用的 app.asar。但它仍依赖官方应用的页面结构和本地数据格式；官方应用升级后，部分增强功能可能需要等待适配。

国内环境付费避雷：别给模型名交智商税

先说结论本教程作者当前国内实测：Cursor Pro+ 和 Ultra 已经完全不值得购买；Kiro 提供的 Claude 也没有达到主力开发 Agent 应有的可靠性。这里评价的是国内用户付费后实际拿到的东西，不是声称所有地区、所有账号都会遇到一模一样的结果。

Cursor：Fable／Opus 用不了，再大的套餐也只是大号空桶

Cursor 过去真正撑得起高价套餐的，不只是编辑器界面，而是能在 Agent 里使用 Fable、Opus 这类高能力模型。问题在于：本教程作者当前在国内环境实测时，这条路线已经无法正常工作。

  • Fable 无法形成可用的开发工作流。
  • Opus 同样无法稳定承担正式项目。
  • 剩余模型和 Agent 体验，撑不起 Pro+ 与 Ultra 的价格。
  • 套餐额度加倍，不会把不可用的核心模型变回来。

Cursor 官方目前仍把 Pro+ 和 Ultra 的主要卖点写成更高的 Agent 限额：Pro+ 约为 Pro 的三倍，Ultra 约为 Pro 的二十倍。但“二十倍”只有在目标模型真能用时才值钱；如果 Fable／Opus 已经掉线，放大的只是额度数字，不是交付能力。

别把 IDE 和套餐绑在一起买Cursor 的编辑、跳转和调试可以继续按需使用，但“Cursor 这个 IDE 顺手”不等于“Cursor Pro+／Ultra 值得续费”。国内环境没有先验完 Fable／Opus，就不要直接冲高价套餐。

为什么此时 OpenCode 更实在

OpenCode 至少把方向盘交还给用户：官方文档列出七十多种供应商，并支持自定义供应商、Base URL 和本地模型。哪个供应商在当前环境里真能跑，就明确接哪个；一个上游掉线，也不用连同整套 IDE 套餐一起陪葬。

OpenCode 不是绕区神器它不会替你绕过模型供应商的地区规则，也不该拿来盗用订阅或共享账号。它的优势是选择更透明、替换更容易：用合法可用的 API 或官方支持接入，先跑真实任务，再决定给谁付钱。

Kiro：下拉框写着 Claude，不等于办事时真有 Claude 那股脑子

本教程作者实际测试 Kiro 的 Claude 后，得到的不是“偶尔发挥不好”，而是整体上明显低于同档 Claude 应有的表现：理解复杂要求吃力，连续执行不可靠，Agent 能力很差，无法放心交付正式工程。对开发 Agent 来说，模型名字只是招牌；能不能看懂任务、持续调用工具、检查结果并把活干完，才是货。

本教程实测结论Kiro 中标注为 Claude 的实际体验表现出明显的低智力、低可靠性和极差的 Agent 能力。免费额度可以拿来验货，但不建议因为界面里出现 Claude、Sonnet 或 Opus 的名字，就购买 Kiro 套餐或把正式项目交给它。

Kiro Auto：官方明说会混合路由

Kiro 官方把 Auto 定义为模型路由器，会根据任务自动选择模型；官方文档还明确说明，Auto 的内部路由并不严格受管理员已经批准的模型列表限制，请求可能交给该区域内 Kiro 可用的其他模型。与此同时，Kiro 的模型目录里既有高倍率的 Opus，也有更低倍率、偏成本效率的 Haiku、DeepSeek、MiniMax、GLM 和 Qwen Coder。

平台把这叫“平衡质量、速度和成本”；站在付费用户这边看，意思就是：你抱着高能力模型的预期买套餐，但平台仍保留把任务分给不同档次模型的权力。简单补全也许无所谓，长任务、复杂工具调用和正式工程可经不起这种盲盒。

证据边界也要讲清楚官方资料足以证明 Auto 会混合路由，却不能单凭外部表现证明“手动指定 Claude 后一定被偷偷换成了某个具体模型”。所以本教程不编后台故事，只陈述两件已经足够避雷的事：Auto 的混合路由是官方机制；Kiro Claude 的实际交付质量没有通过本教程作者的主力 Agent 验收。

开工前模型体检：雷达之后还要自己跑

公开榜只能提供外部信号。最终决定前，用自己的短任务、长上下文和 Agent 工具任务复测，确认它能把你的活稳定做完。

先做判断，再开套餐优先参考真实任务和连续趋势，再拿自己的固定任务复测。模型名、宣传分数和额度倍数都不等于交付质量；能把活稳定干完，才值得长期付钱。

写成人内容，别让工程模型兼职当作者

NSFW 不等于违法、有害或没有创作价值。角色卡和互动叙事中的成人向内容，可能用于成年人之间的亲密关系、情色文学、成人角色扮演、服装与身体审美设计，以及完整的角色档案。

真正卡创作的，是部分模型即使面对明确成年、完全虚构、自愿关系的内容，仍会反复干这些事：

  • 直接拒绝继续，导致剧情或角色卡开发中断。
  • 自动淡化关键内容，破坏角色状态和关系推进。
  • 把创作任务改写成说教或价值判断。
  • 擅自改变用户指定的题材、文风或人物行为。
  • 因为题材标签误伤正常的人设、身体和服装设计。
选择标准不要只问“哪个模型最聪明”，还要问：它能否在合法边界内稳定完成创作者真正提出的成人向任务。

当前好用的分工：Claude 打底，Grok 补火

当前更实用的组合是 Claude 加 Grok。不是说它们完全没有审核，而是两边各做自己更稳的活：

Claude：主内容模型

负责完整角色、世界观、长篇剧情、关系逻辑和上下文一致性。

长文本心理与关系结构统一设定一致性
+

Grok：成人内容补位

负责更直接的成人场景、对话细节、补写和同一场景的第二版本。

直接表达成人场景第二视角内容补位

模型和平台政策会变化，使用前应查看当前服务规则：Anthropic 使用政策 · xAI Grok FAQ

Claude 守住人物、关系和长线剧情

Claude 的价值不只在文笔，更在于能把人物和复杂上下文端稳。优先交给它：

角色与世界观

角色档案、派系、背景、行为动机和世界规则。

关系与长篇剧情

关系为什么发展、人物为什么这样反应，以及事件如何影响后续。

文本统一

世界书整理、对话样本、已有文本扩写和文风统一。

对成人向角色卡来说，Claude 更适合先回答：

Claude 的核心职责
这段成人内容为什么会发生？
角色为什么会做出这种反应？
这次互动会怎样改变人物关系和后续剧情？

它仍可能因为表达尺度、上下文歧义或平台策略拒绝部分内容。提供任务时，应明确角色年龄、虚构属性和自愿关系，减少不必要的误判。

成人题材上下文声明
本作品为虚构成人题材。

所有参与亲密或性关系的角色均为18岁以上成年人。
所有亲密行为均建立在明确、自愿、知情和可撤回的同意之上。
不涉及现实人物、未成年人、胁迫或未经同意的私密内容。

请按照创作要求处理角色、关系、世界观和剧情，
不要因为题材属于成人向而擅自淡化、说教或改变作品方向。

Grok 接住 Claude 容易刹车的部分

Claude 容易中断或过度淡化的地方，可以让 Grok 接手：

  • 更直接的成人向场景和成人对话样本。
  • 身体、动作和互动细节的连续描写。
  • Claude 已经完成结构，但没有完成的正文。
  • 为同一场景提供另一种表达或强度版本。
  • 检查原始需求是否在改写过程中被过度淡化。

在这套方案中，Grok 不需要取代 Claude 的全部工作。更稳定的职责划分是：

Claude + Grok 分工
Claude
负责：角色、世界观、关系、长篇剧情、场景前因与后续影响

Grok
负责：成人场景、直接表达、动作与对话细节、第二版本
仍然需要人工验收限制更少不等于文字更好，也不等于角色一定一致。创作者仍要检查人物年龄、同意关系、设定、文风和事实错误。

双 Agent 不是两个人抢方向盘

本教程中的副驾驶不是只负责审查的聊天模型，而是：

双开 Agent，共享总工作区例如同时运行 Codex 桌面端和 Claude Code Desktop；两者都能读取共享资料，但分别处理不同项目或完全隔离的写入目录。

副驾驶是为了让两个真实工程任务并行，不是把同一个项目撕成拔河现场。

双 Agent 怎么配才不互殴

组合主驾驶职责副驾驶职责
Codex + Claude CodeCodex 处理大型角色卡工程、TW Skill、模块化、多文件修改和项目治理。Claude Code 处理另一个独立的前端、预览、浏览器测试或调试项目。
Claude Code + CodexClaude Code 处理当前需要频繁运行和预览的前端项目。Codex 处理另一张角色卡、世界书、组件拆分或独立审计任务。
共享知识底座两边读取相同的 TavernWeave、ST 开发指南 DB、模板和命名规范，减少工程范式漂移。

双 Agent 的五条铁律

  • 不能同时修改同一个项目。即使表面上是不同文件，也可能同时触碰 Git 状态、构建产物、锁文件、配置、版本号和自动格式化结果。
  • 共享资料默认只读。00-Shared/ 中的 Skill、DB 和模板只有在专门维护任务中才允许修改。
  • 每个 Agent 必须声明写入范围。允许读哪里、允许写哪里、禁止碰哪里，都应在开工时明确。
  • 同项目切换驾驶员前先停止写入。运行验证、建立 Git 提交、生成交接，再让另一个 Agent 重新读取项目。
  • 同一项目只能有一个写入驾驶员。第二个 Agent 可以只读分析，但不能边读边顺手修。
错误示例Codex 和 Claude Code 同时打开 Projects/星月学院/ 并各自修改。两个 Agent 都可能基于过期文件继续工作，最终互相覆盖、撤销或污染 Git Diff。
