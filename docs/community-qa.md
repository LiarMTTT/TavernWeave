# TavernWeave 社区常见问题 Q&A

这份问答收的是 TW 讨论帖里大家反复问的问题，意思相近的合成了一题。答案按当前 **v1.6.0** 的仓库说明和 Skill 的实际分工来写；帖子里较早的说法如果和这里不一样，以当前仓库为准。

不同客户端、酒馆版本和模型服务，表现可能不一样。凡是“装上后到底能不能用”“导进酒馆能不能跑”这类问题，最后都要在你自己的环境里实际试一次。

## 怎么读这份问答

问题按四个阶段分组：新人／萌新、入门、熟练、老手。分组只是告诉你这题大概什么时候会碰到，不是给人定级，跳着看也没关系。

先把几个常见词对一下：

| 原词 | 大白话 |
| --- | --- |
| TW | TavernWeave，就是本仓库这套 Skill |
| ST／酒馆 | SillyTavern，玩角色卡用的软件 |
| Agent | 能读你的文件、跑命令、帮你干活的 AI 助手 |
| 客户端（宿主） | Agent 工作的软件，比如 Codex、Claude Code |
| Skill | 给 Agent 看的分工说明书，碰到对应任务时读取 |
| Host Front Door | 客户端每次开任务时读取的 TW 入口规则，可选，推荐装 |
| Library | TW 随包带的资料库，里面有开发指南、设计和动效参考，按需查 |
| 世界书 | 满足关键词或条件时，自动塞进提示词的设定条目 |
| 变量／MVU | 变量是会随剧情变的数据，比如好感、日期、地点；MVU 是一套常用的变量更新方案，让模型在回复里顺带改变量 |
| Zod／schema | 规定变量有哪些字段、每个字段是什么类型的“格式表” |
| EJS | 一种提示词模板写法，能按变量决定哪段内容发给模型 |
| 正则 | 按规则找文本并替换，常用来改显示效果，或把界面挂到消息里 |
| 酒馆助手 | Tavern Helper（JS-Slash-Runner），让卡能跑脚本、显示网页界面的 ST 扩展 |
| 楼层 | 聊天记录里的一条消息 |
| iframe | 嵌在消息里的小网页框，状态栏常装在里面 |
| 源码／成品 | 源码是拆开、方便修改的项目文件；成品是打包出来、能直接导入酒馆的 JSON 或 PNG |
| 实机测试 | 把成品导进真正的酒馆，照着玩一遍 |
| 续接记录 | 写着目标、进度和下一步的交接笔记，比如 `NEXT.md`，换会话时靠它接着做 |
| token | 模型计算文字量的单位，用得越多越贵，也越占上下文 |

## 一、新人／萌新：先弄明白、装好、跑通第一件事

### Q01. TW 是软件、插件，还是一张角色卡？

**A：** 都不是。TW 是一套装进 Agent 客户端的 Skill，也就是给 AI 助手看的工作说明书。它不装进酒馆，也不能当角色卡导入。

装好以后，Agent 会照着它的方法帮你规划、制作、检查角色卡、网页和小工具。做出来的东西，再放到酒馆或对应的软件里用。

### Q02. ChatGPT、Codex、Claude Code、Agent 和 TW 是什么关系？不会写代码能用吗？

**A：** 可以这样理解：Agent 是干活的 AI 助手；Codex、Claude Code 是它干活的地方；TW 是交给它的分工说明和参考资料。普通 ChatGPT 聊天窗口默认没装 TW，一般也读写不了你电脑上的项目文件，所以不能和这种工作环境混为一谈。

不会写代码也能开始。你要讲清楚四件事：想做什么、手上有什么材料、哪些东西不能动、做到什么程度算完成。其余的交给 Agent，同时要求它把关键选择讲给你听，最后交一个你能亲手试的版本。

### Q03. 我到底要下载或安装哪些东西？STDB、AFV 要另装吗？

**A：** 只用 TW 自带的资料的话，不用另装。你要准备的是：

1. **TW 的全部 22 个 Skill**：从本仓库或正式发行包安装。
2. **Host Front Door**：可选，推荐装。
3. **酒馆（ST）本体**，以及你的作品自己需要的扩展或依赖，按作品需要单独准备。

STDB 的正式指南和筛选过的 AFV 设计、动效参考，已经打包进 TW 自带的 Library，按需读取，不用再另装完整的 STDB 或 AFV 仓库。

### Q04. 安装时给 Agent 什么指令？工作目录选哪里？

**A：** 安装指令直接用 [README 的安装指令](../README.md#安装与更新)，要求 Agent 按仓库 `skills/` 的完整清单安装，最后核对 `22/22`。

这里有两个容易混的文件夹：

- **安装位置**：客户端实际会去找 Skill 的那个 `skills` 目录。TW 的源码文件夹不算，拿源码文件夹来核对“装好了没有”，等于查错了地方。
- **工作目录**：做角色卡时，选这张卡的项目根目录。开工前先让 Agent 读项目说明、源文件和续接记录。

### Q05. 可以在手机、网页端或 DeepSeek Harness 上直接用 TW 吗？

**A：** 要看那个环境能不能做到三件事：找到并读取 Skill、读写需要的文件、调用工具。

仓库正式支持的是 Codex 和 Claude Code。DeepSeek Harness 目前只有实验适配说明，还没有完成真实安装、模型调用和酒馆里的实测。手机或网页能打开一个 AI 对话，不代表它已经加载了 TW。先确认上面三项能力，再实际叫它用一次 Skill 试试。

### Q06. 从哪里开始学？必须先学完所有术语和指南吗？

**A：** 不用先学完。从 [新人教程](newbie-guide/index.html) 和一个很小的目标开始就行，比如做一张纯文本卡，或者修一个明确的显示问题。

先想清楚三件事：想得到什么、手里有什么、做好了怎么试。Agent 会按问题去读需要的资料。碰到看不懂的词，直接问它：“用大白话说说，这个词在这次任务里是干嘛的？”

### Q07. 显示安装成功了，客户端就一定会用吗？

**A：** 不一定，要分两步确认。

1. **文件齐不齐**：对实际安装目录运行仓库自带的核验器。看到 `INSTALLATION VERIFIED: 22/22`，说明 22 个 Skill 文件齐全、和仓库一致。
2. **客户端用不用**：新建一个任务或重启客户端，让 Agent 实际调用一个 Skill，并说出它读了哪个入口、做了什么。

做到第二步，才算客户端真的找到并用上了。全局规则文件存在，也只算第一步。

### Q08. 第一次向 TW 提需求，怎样说最省事？

**A：** 一句目标，再加三样信息：手上有什么材料、哪些不能改、第一版做到什么程度就算成。比如：

> 我想做一张现代悬疑纯文本卡；只有这份人物设定；保留主角关系；先做一个能导入 ST 并聊三轮的版本。

哪一项还没想好，就直接写“你推荐”。Agent 要说出推荐的理由，创作方向还是由你来定。

### Q09. 模型、API 和费用由 TW 提供吗？新手选什么？

**A：** 不提供。TW 不送模型额度，也不带 API Key。

选模型和服务时，先确认你的客户端配上它以后，能读文件、能调用工具、能撑住比较长的任务；然后拿一个小任务试，比比花费、速度和效果。价格和能力经常变，以服务方当时的页面和你自己试出来的结果为准。

API Key 不要贴进聊天，也不要写进角色卡文件。

### Q10. TW 能解除模型拒答、平台限制或自动处理所有成人内容吗？

**A：** 不能。TW 管的是创作和制作流程，改不了模型提供方和平台的规则。

内容被拒时，可以把允许处理的部分单独拿出来说，比如角色设定、卡的结构、界面或技术问题。别把“装了 TW”当成绕过限制的办法。

### Q11. “新人、入门、熟练、老手”会改变功能或作品质量吗？Soul 又是什么？

**A：** 不会。四个挡位只影响讲得有多细、一次走多大一步，功能和质量要求完全一样。挡位由你自己选，Agent 不能看你表现如何就自作主张换挡。

Soul 是当前任务里可以打开的一种教学或审查语气。它不会让 Agent 多出改文件、发布之类的权限，也不能代替事实核对。退出 Soul 以后，大白话和你选好的挡位照常有效。

## 二、入门：把第一个作品做出来

### Q12. 做第一张角色卡，合理顺序是什么？

**A：** 大致五步：

1. 定下这张卡怎么玩、有哪些人物，第一版做到哪里就算能玩；
2. 选能做到这些的最简单结构；
3. 写开场和必要的设定，准备好要用的依赖；
4. 导出一张试用卡，导进你要用的酒馆里真聊几轮；
5. 每轮根据看到的问题，修一两处明确的地方。

状态栏、数据库和复杂脚本，不用一开始就全装上。

### Q13. 我只有模糊想法，或只想改一个小地方，Agent 会不会把项目做大？

**A：** 有这个风险，所以一开始就把范围说清楚。

- **新项目，只有模糊想法**：先让 Agent 把总设计和第一版能玩的范围收住，再动手。
- **已有作品，只改一点**：先让它读现状和续接记录，只改跟这次目标有关的地方。

可以直接这样说：“这轮只改开场，其他都别动；改完告诉我，导入后要看哪几处。”如果它想扩大范围，要先说明这跟你的目标有什么关系。

### Q14. 接手别人做的卡，只有 PNG 或 JSON，能直接续更吗？

**A：** 能接手，但先别急着改。先让 Agent 查清这张卡里实际装了什么，讲清它是怎么运作的，再决定是“沿着原作继续维护”，还是“拿它做二创”。

PNG／JSON 是打包好的成品，里面不一定有方便维护的源码。没有源码，就要记下哪些部分只能从成品里拆出来还原。另外还要确认三件事：

- 哪些人设必须保留；
- 旧聊天和存档还能不能接着用；
- 第一次先改的最小一处是什么。

### Q15. 小说、图片和网页资料很多，怎么给 Agent 才不乱编？

**A：** 先分清三类内容：原作写的、二创设定的、你自己拍板的，并标明是哪个版本或哪几章。

TW 的作品资料库能把文字资料整理成可以编辑的 Markdown 和索引，之后能按来源、改编版本和剧透阶段（剧情进行到哪一步才揭晓）回头查。图片和网页参考，也要记清出处和用在哪里。

Agent 没读到的内容，要标成“待核实”，不能拿模型的印象当原作事实。

### Q16. Skill 会自动全开吗？我需要逐个点名吗？

**A：** 不会全开，也不用逐个点名。直接说要做什么，Agent 应该自己挑最相关的 Skill，再从 Library 里读需要的指南；只有工作确实跨了好几个领域，才会几个 Skill 一起用。

你也可以点名要某个 Skill。但要留意：仓库里有这个 Skill，不代表这次任务真的读了、用了它。

### Q17. 纯文本卡、MVU、MVU Zod、数据库卡该怎么选？

**A：** 从简单往复杂加，够用就停：

- **纯文本卡**：只需要人物、世界和对话规则。先从这里开始。
- **变量系统（常用 MVU）**：要跨多条消息记住并更新数值或剧情状态，比如好感、日期、任务进度。
- **MVU Zod**：在 MVU 基础上用 Zod 规定变量的格式，会多出特定的结构要求和运行依赖。
- **数据库式设计**：记录、查询、数据升级（迁移），以及多个界面都要读同一批数据，确实复杂到这个程度，才把卡当成小数据库来设计。

不管选哪条，先确认你的酒馆版本和扩展版本支持它。

### Q18. 世界书、角色设定、开场和 NPC 信息分别放哪儿？

**A：**

- **角色设定**：角色是谁、核心怎么行事，这些稳定的内容放在卡的基本设定里。
- **世界书**：只在特定场景或话题才需要的知识，按触发条件放进世界书。
- **开场**：负责把玩家带进一个具体的起点。
- **NPC**：一直都重要的，留一段固定摘要；只在某个地点或事件出现的，按条件触发详细资料。

写完用实际聊天查两件事：该出现的内容有没有触发；同样的内容有没有重复塞进提示词、白占篇幅。

### Q19. 我想要开场页面、状态栏或控制中心，该从哪一种做起？

**A：** 先看它们各管什么：

- **开场页面**：开局时让玩家做一次设置，然后发出真正的第一条玩家消息。
- **状态栏**：放经常要看的当前状态。
- **控制中心**：处理比较复杂的设置和管理。

动手前先写清楚：数据从哪来、什么时候更新、玩家能改什么，再挑能满足需求的最小界面。只有几个开场选项，一般用不着做成完整应用；复杂的管理操作，也别全塞进状态栏。

### Q20. 做完后交付什么：源码、JSON、PNG，还是截图？

**A：** 看用途：

- **以后还要改**：要有源码。
- **导入酒馆**：一般是项目打包出来的 JSON，或者带卡数据的 PNG。
- **截图**：只用来展示界面长什么样，证明不了卡能导入。

打包时要检查需要的世界书、正则、脚本和图片是不是真的进了成品，并写明版本、说清测过哪些。

### Q21. 为什么“自动测试通过”了，还要进真实酒馆试？

**A：** 因为有很多问题只有在酒馆里才会暴露。自动检查能找出文件、结构和一部分规则的错；离线网页预览能看布局。但导入、消息显示、扩展注入的内容、变量更新、重新加载和数据保存，都要看真实的酒馆和你装的扩展。

至少把试用卡导进你要用的那个版本，把这次改动相关的操作走一遍，比如开场、对话、编辑消息或切换聊天。

### Q22. 任务太长中断了、Skill 更新了，怎样接着做？

**A：** 靠续接记录，不靠聊天记忆。结束前留好这些：项目目标、已经确认的决定、当前源码和成品的版本、做过哪些检查、哪些还没验证、下一步做什么。

开新任务时，先让 Agent 读仓库里的 `AGENTS.md`、`NEXT.md` 或同类续接记录，再看实际文件。更新 Skill 以后，先核对安装目录，再开新任务，让客户端重新找到它们。旧聊天里的结论，不能拿来证明新环境已经用上了新版本。

## 三、熟练：变量、渲染、界面和流程故障

### Q23. 世界书条目的触发、顺序、深度和提示词占用怎么调？

**A：** 没有通用数值，要对着你的酒馆版本调。

1. 先确认你用的 ST 版本里，每个设置到底是什么意思；
2. 把每个条目的触发条件、插进提示词的位置、谁优先、占多少篇幅记下来；
3. 准备“应该触发”和“不该触发”两组聊天样例去试。

剧情变乱时，先查三样：同一内容是不是重复插入了、谁把谁覆盖了、有没有条目太长。查完再动参数。

### Q24. MVU 变量第一次没有值，或者更新停了，先查哪里？

**A：** 按这条链一段一段查：

**字段定义 → 初始值 → 更新规则 → 模型能看到的内容 → 运行时读取 → 界面显示**

每一段都要在几种情况下试：新开聊天、换不同开场、编辑或重新生成、切换聊天、重新加载页面。有些开场方式，要等玩家真正发出一条消息，变量才会进入正常的更新流程。

两个常见误区：

- 状态栏显示旧值，不能直接断定模型没更新，也可能是中间某一段断了；
- 不要用脚本假装触发了初始化，把中间缺的一环盖过去。

### Q25. 变量、EJS、世界书、脚本、正则到底各管什么？

**A：**

| 部分 | 管什么 |
| --- | --- |
| 变量 | 存会随剧情变化的数据 |
| 世界书 | 满足条件时提供知识或规则 |
| EJS 等提示词模板 | 决定怎样把信息送给模型 |
| 脚本 | 必须算准、每次结果都一样的读写和交互 |
| 正则 | 找到特定文本并改写 |

分好工以后，给每项数据定一个唯一的来源，写清谁写、谁读、什么时候刷新。别让五个地方各自维护同一个状态。

### Q26. 剧情写着过了一天，状态栏的时间却没变，怎么定位？

**A：** 先搞清“时间”是从哪来的：模型写在正文里、存在 MVU 变量里，还是脚本算出来的。

再找两处：哪一步负责把剧情里的时间变化写回变量；状态栏在等哪个更新事件。

然后拿同一段聊天，对照三样东西：消息原文、变量当时的值、界面上显示的值。这样才能分清是模型没写、写入失败，还是界面没刷新。

### Q27. 正则改了却没生效，或者误伤了开场／正文，怎么查？

**A：** 逐项核对：

- 有没有启用；
- 作用在哪类消息上；
- 改的是显示给你看的内容，还是发给模型的提示词；
- 深度和替换顺序。

然后用最短的样例文本分别试“应该匹配的”和“必须原样保留的”。

如果这条正则还负责把界面挂到消息里，还要确认替换后的网页结构（DOM）和脚本加载路径对不对。离线样例通过以后，仍要在真实酒馆里，看消息从生成、显示到编辑的整个过程。

### Q28. 电脑上正常，手机或窄屏就错位，先查什么？

**A：** 先量真正装着界面的那个框有多宽，通常是消息区域或 iframe，而不是整个浏览器窗口。

然后查：写死的宽度、内容溢出、缩放、按钮够不够大、长文本会不会撑破。用窄框预览试完，还要在目标设备上的酒馆里再试一次。离线截图看着没问题，说明不了手机酒馆里的加载、滚动和点击都正常。

### Q29. SVG、图片、音频、视频或 Live2D 放进卡里，怎样避免失效？

**A：** 先定资源放哪：直接塞进成品、跟着项目一起发，还是从网上加载。然后记下来源、授权、文件大小、要不要提前加载，以及加载失败时显示什么。

检查最终的 JSON／PNG 里真的带着这些资源，或者外部地址在你的环境里打得开。会动的媒体，比如音视频和 Live2D，还要在真实酒馆里看启动、切换、关掉时的表现，以及在手机上的样子。

### Q30. Agent 说“会用工具”，却没调用 MCP 或 Skill，该怎么办？

**A：** MCP 是让 Agent 连接外部工具的接口。遇到这种情况，让 Agent 拿出实际记录：这轮读了哪个 Skill 入口、用了什么工具、输入了什么、得到了什么能检查的结果。拿不出记录，就按“还没调用”处理。

如果是工具本身用不了，先查三样：客户端有没有识别到这个工具、权限够不够、工作目录对不对。再把问题缩小到一个能重现的动作。Agent 写出来的计划只是打算，不能当作已经做过的证明。

### Q31. 打包后导入是空卡、缺世界书、图片只有壳，怎么排查？

**A：** 从头往后追：

**维护源码和构建设置 → 最终 JSON → PNG 里嵌的卡数据是否和 JSON 一样**

逐项看名字、开场、世界书、正则、脚本和要用的资源在不在。然后用一张全新导入的测试卡验证，免得旧卡的缓存或旧聊天把问题挡住。

还有一点：如果项目自己没有构建工具，不能因为 TW 有某个 Skill，就以为已经有现成的打包命令。

### Q32. 多 Agent 分工、换模型、控制 token，什么时候值得做？

**A：**

- **多 Agent 分工**：资料整理、某个模块、某项检查这类能各自独立完成的工作，才适合几个 Agent 并行。共用同一份状态、同一个浏览器、同一份打包输出的工作，要统一安排，不能各干各的。
- **换模型**：先定好共同目标、每个文件归谁管、怎样算合格，再拿实际任务比表现和花费。
- **省 token**：先删重复资料、把任务范围说清楚、留好续接记录。别为了省钱随手删掉必要的规则。

### Q33. 更新了 TW、ST 或扩展，旧任务的结论还能用吗？

**A：** 一部分能用。创作目标和你确认过的决定可以照用；安装目录、API 的表现、扩展事件和实际运行结果，要按新版本重新查。

- **更新 TW 后**：核对 `22/22` 和全局规则状态，再开新任务实际调用一次 Skill。
- **更新 ST 或扩展后**：把受影响的操作在真实酒馆里重新跑一遍。

记录时写明是“旧版本测过”还是“当前版本测过”。

## 四、老手：复杂架构、性能、维护与发布

### Q34. 复杂计算和数据库逻辑，交给模型、提示词还是脚本？

**A：** 各做各擅长的：

- **脚本**：要算准、每次结果都一样的公式和数据升级。
- **模型**：写剧情、提出可选方案、做开放式判断。
- **提示词**：告诉模型规则是什么、输出不能越过哪些边界。
- **数据库结构**：定字段、每条记录的唯一编号（主键）、存在哪里、版本号。

每个关键数值都写清楚：从哪来、谁写、谁读、出错了怎么办。别让模型既当数据库又当计算器。

### Q35. 数据库卡能在同一楼层完成所有更新吗？

**A：** 目前还不能这么承诺。TW 的数据库卡方案，支持的是正常的多轮对话：状态跟着一条条消息（楼层）保存。在同一条消息里完成全部更新，也就是同楼层方案，还没有验证过。

设计时要把“数据存在哪”写进约定，也别让备用方案偷偷把数据换个地方存。要说某个具体做法支持同楼层，得先在你的酒馆里实测过：新建聊天、编辑、重新生成、切换聊天、数据保存都没问题才行。

### Q36. 大卡变慢，怎样知道是提示词、世界书、正则、脚本还是媒体拖的？

**A：** 分两步：

1. **先数清楚**：拿同一版成品，分别统计文件大小、提示词长度、世界书条目数、正则数、脚本数和内嵌媒体，作为基准。
2. **再实测**：在一个写明版本的真实环境里，测首次打开、重新生成、切换聊天、打开控制中心这些场景。

按耗时或体积找出是哪一部分拖慢了，先做最小、随时能撤回的优化，再用同样的统计方法和基准比。用 Node 在电脑上跑出来的静态计时，说明不了真实酒馆里流不流畅。

### Q37. 旧卡只改一个组件，还需要整卡重做和重新验收吗？

**A：** 不用整卡重做，但该测的还得测。

先圈出这次改的是哪个组件、它依赖什么、会影响哪些地方，只改维护源码里对应的那部分，再用项目自己的工具重新打包。

回头检查要覆盖受影响的链路，以及原来重要的功能，也就是改完再试原来能用的地方；跟运行有关的，照样要在真实酒馆里试。别因为“只是小改”就跳过成品内容的检查，也不用把不相关的设计全部推翻重来。

### Q38. 独立前端、嵌入式界面和普通状态栏怎么取舍？

**A：** 看四样：交互有多复杂、数据归谁管、在哪运行、维护起来多费劲。

- 经常看、很少改的状态：轻量状态栏；
- 开局时选一次：开场页；
- 大量设置和管理操作：才考虑控制中心。

如果独立前端或同楼层方案在酒馆里没有可靠的支持，Agent 应该直说不推荐，先给更轻的办法。就算只是做个原型试试，也要留着“真实酒馆里测过才算数”这一关。

### Q39. 从设计到发布，哪些检查可以合并，哪些不能互相代替？

**A：** 同一个改动的自动检查可以一起跑，但结果要分开记，因为它们说明的是不同的事：源码检查、自动测试、离线成品检查、浏览器预览、真实酒馆测试、人工验收、Git 提交、发布许可。

剧情和画面你满不满意，只能你自己说了算，自动检查替不了；真实酒馆里跑通了，也不等于同意公开发布。每一关都记下对应的版本，以及还没测的部分。

### Q40. 怎样给角色卡做一次“健康检查”或全量架构审查？

**A：**

1. 先定好查哪些内容、查哪一版成品；
2. 读维护源码、打包过程和运行依赖；
3. 分块看：提示词与世界书、变量链路、正则与脚本、界面、安全、性能、交付。

报告里要列清楚：哪些查完了、哪些只查了一部分、哪些没读、哪些有意排除。每个问题都附上依据、影响和修法。只读审查只能说明“发现了什么”，不能当作“已经修好”，也不能当作“已经在酒馆里测过”。

### Q41. 不同客户端或扩展版本的 API 表现不一样，TW 给的例子还能照抄吗？

**A：** 别直接照抄。先查清你用的 ST、酒馆助手（Tavern Helper／JS-Slash-Runner）等的实际版本和官方接口，再把例子改成适合这个环境的写法。

宏、事件、变量接口、正则在哪个阶段执行、iframe 什么时候加载和销毁，都可能让结果不同。先用最小的例子把调用试通，再接进整张卡。TW 提供的是核对方法，不保证任何一段代码换了版本还能直接用。

### Q42. 能不能把 TW 的 DeepSeek Harness 适配说成“正式兼容”？

**A：** 不能。仓库目前只写了实验适配，以及在不同工具配置下怎样暴露 Skill；还没有真实安装、模型调用和酒馆实测的证据。

对外介绍时要保留“实验”两个字，并写清到底验证了哪些。等目标环境里安装、找到 Skill、调用工具和做出实际作品都跑通了，再更新说法。

### Q43. 发卡、打包或公开作品前，最后要核对什么？

**A：** 按这张清单过一遍：

- 固定源码和准备发布的版本；
- 依赖、国内／海外加载地址的选择、世界书和内嵌资源都齐全；
- JSON 和 PNG 里的卡数据一致；
- 在目标酒馆里把关键操作走一遍；
- 列出哪些做过自动检查、哪些实机跑过、哪些经过人工确认、哪些还没验证；
- 素材来源和使用授权单独核对。

提交源码、交付成品文件、公开发布是三件事，各自按项目约定和授权来。

### Q44. Skill、Soul、Library 或设计参考“已经存在”，就表示它被采用或验收了吗？

**A：** 不表示。从“有”到“验过”，中间还隔着好几步：

**存在 → 这轮读过 → 项目选用 → 写进源码 → 在客户端或酒馆里真的跑起来 → 你认可**

Library 挑选页里的候选项，只说明“可以考虑”；Soul 只改说话风格，不改变该做的检查和该拿的授权。每个“已完成”的说法，都应该能对上实际的执行记录或对应的成品。
